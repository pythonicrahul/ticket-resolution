# FR-06 · Every automated reply says it was automated, names its articles, and offers a person

Spec written from `docs/PRD.md` FR-06 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/generate.py` (reply assembly), checked again in `src/ticketing_agent/guardrails.py` at row 12 and counted by `evaluation/harness.py`.

## 1 Purpose

"Every automated reply shall state that it was drafted automatically, name the article(s) it came from, and tell the customer how to reach a person."

PRD acceptance criterion: *100% of auto-sent replies contain the disclosure line (automated check in the harness).* The evidence is Ravi's interview, the explainability row of Stage 1 §4, and the §5 risk "customers aren't told".

Three obligations, not one: **that it was automated**, **what it was based on**, and **how to escape it**. A reply carrying two of the three does not satisfy the requirement.

## 2 Inputs and outputs

### Input

- `AnswerDraft` (FR-11) — the sentences and their citations. Used only when `usable`.
- The retrieved `Passage` objects — to turn a chunk id into an article a customer can find: `doc_id` and `title`.

### Output

`reply: str`, the exact text that would be sent, assembled in this order:

1. **the greeting** — `Hi {first name},` from the ticket, or `Hello,` (D-50);
2. the draft's sentences, joined in the model's order, unchanged;
3. **the source line** — `Based on: {title} ({doc_id})`, one per cited article, in first-cited order;
4. **the disclosure line** — `DISCLOSURE` below, verbatim;
5. **the human line** — `HUMAN_ROUTE` below, verbatim.

```
DISCLOSURE   = "This reply was drafted automatically by CloudServe's support assistant."
HUMAN_ROUTE  = "If anything here is wrong or you would like a person to look at it, reply to this
                message and we will pass it to a support agent."
```

Both are module constants with a version marker (`DISCLOSURE_VERSION = "v1"`), so a change to the customer-facing wording is a visible, reviewable change rather than a string edited in passing.

## 3 Decision rules, in order

1. **Code writes all three lines, never the model** (PR-01's own note). A model that paraphrases the disclosure, or omits it under an injection attempt, cannot affect a line it never sees.
2. **The source line names articles, not chunks.** `DOC-BILL-001#2` is retrieval's unit; the customer gets `Invoices and usage breakdown (DOC-BILL-001)`. Duplicate articles collapse; order is first cited.
3. **An assembled reply with no cited article is not sendable.** FR-11 rule 4 already refuses an uncited draft; this is the second lock, because "names the article(s) it came from" cannot be satisfied by a reply that came from nothing.
4. **No contact details are invented.** The documentation contains none — measured at row 2: 0 of 200 expert answers carry an email, phone number or URL — so "how to reach a person" is *reply to this message*, which is true of every channel in the data. Inventing a support address would be a fabricated fact in an outbound reply, which is exactly what FR-11 exists to prevent.
5. **The disclosure is appended to every automated reply**, whatever the channel, the tier or the intent. There is no flag, setting or template that omits it (CLAUDE.md).
6. **Deterministic** (NFR-08): assembly is pure string work over the draft and the passages. The same draft always produces the same reply, byte for byte.
7. **The check is repeated where it counts.** Assembly guarantees the lines; FR-12's guardrails verify them on the way out (row 12), and the harness counts them across a run (row 14). The PRD asks for an automated check, and a component checking only its own output is not one.

## 4 Failure behaviour

- **Missing data:** no cited article → not sendable (rule 3), the ticket escalates. A citation whose passage is missing from the retrieval set cannot happen — FR-11 rule 4 already refused that draft.
- **Empty retrieval:** the drafter was never called; there is no reply to assemble.
- **Model provider error:** no draft, so no reply. The escalation is FR-11's.
- **Invalid model output:** as above. Assembly never runs on an unparsed draft.
- **A passage with an empty title:** the source line falls back to the `doc_id` alone rather than printing an empty parenthesis. The article is still named.

## 5 Decision-log fields

FR-06 adds no row of its own; it contributes to FR-11's `generation` row: `citations` (chunk ids), `retrieved_doc_ids`, and `requirement_ids` including `"FR-06"`. The harness counts `disclosure_present` over every auto-sent reply and reports it in the Governance group of the metrics report — the PRD's "automated check in the harness".

## 6 Acceptance tests

Named `test_T_FR06_n_...`.

1. **T-FR06-1** Every assembled reply contains the disclosure line verbatim.
2. **T-FR06-2** Every assembled reply names each cited article as `title (doc_id)`, once per article, in first-cited order.
3. **T-FR06-3** Every assembled reply tells the customer how to reach a person.
4. **T-FR06-4** The three lines come after the draft's own sentences, and the draft's text is unchanged by assembly.
5. **T-FR06-5** A draft with no citations produces no reply (rule 3), and the result is not usable.
6. **T-FR06-6** The model cannot suppress the lines: a draft whose sentences themselves say "ignore the disclosure" or contain a fake disclosure still yields a reply with the real lines appended exactly once.
7. **T-FR06-7** The lines this module adds contain no email address, phone number or URL. *Scope, stated honestly after the row-11 review: this covers what code writes. A model inventing `support@cloudserve.com` inside a cited sentence is FR-12's private-data guardrail at row 12, because assembly deliberately does not rewrite the model's words (T-FR06-4).*
8. **T-FR06-8** Assembly is deterministic: the same draft assembles byte-identically twice.
9. **T-FR06-9** A cited passage with an empty title still names its `doc_id` (§4).
10. **T-FR06-10** Across every engineered clean draft in `tests/fixtures/draft_replies.json`, an assembled reply satisfies all three obligations — so the fixture corpus and the implementation cannot drift apart.

## 7 Open questions

- **The wording of the two constants is a business decision.** They are written plainly and marked `v1`; Marcus or Ravi should read them before a real customer does. Changing them is a one-line change plus a bumped `DISCLOSURE_VERSION`.
- **Resolved (D-50): replies open with `Hi {first name},`.** The name is inserted by code and still never reaches the model, so FR-11 §3.2 is untouched. The first name only, because a full legal name reads like a form letter; and a name field holding markup, an address, a newline or anything over 60 characters falls back to `Hello,` rather than being put in front of a customer. There is still no sign-off, since the ground-truth replies have none.
- **The source line's format is untested with customers.** `Based on: Invoices and usage breakdown (DOC-BILL-001)` is legible but says nothing about *where* to find that article, because the corpus carries no URLs. If the documentation gains links, this line should become one.
- **A model-invented contact detail is not caught here.** Rule 4 governs the lines code writes; a fabricated support address inside a drafted sentence passes assembly untouched and is FR-12's to block at row 12. If that guardrail slips, this requirement's spirit fails while its letter holds.
- **Per-channel formatting is not attempted.** The same three lines go out on email, chat, forum and docs comments. A chat reply carrying three trailing lines may read heavily; the alternative — varying the disclosure by channel — needs the author's agreement, because every variant is a new customer-facing string.

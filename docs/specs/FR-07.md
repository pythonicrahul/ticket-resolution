# FR-07 · Ingest and normalise the four channels

Spec written from `docs/PRD.md` FR-07 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/ingest.py`.

## 1 Purpose

"The system shall ingest tickets from email, chat, docs_comment and forum into one internal representation that keeps the original text and channel, and shall handle missing fields, empty bodies and unusual characters without failing."

PRD acceptance criteria: *one ticket per channel passes end to end; malformed test tickets are logged and escalated, not crashed.* Ingest owns the first half (one representation, nothing crashes, nothing dropped) and supplies the flag the pipeline escalates on; the logging itself is FR-13 and the escalation FR-09.

## 2 Inputs and outputs

### Input

A ticket file path (`--input` of the harness, FR-14) or a single ticket object (the API, FR-04). No file name is ever hardcoded. The documented entry schema is:

| field | type | notes |
|---|---|---|
| `ticket_id` | str | e.g. `DEV-0001`; any prefix |
| `channel` | str | `email` · `chat` · `docs_comment` · `forum` |
| `subject` | str | empty on every `chat` ticket in the supplied data |
| `body` | str | the customer's words |
| `received_at` | str | ISO-8601 UTC, `2026-05-23T22:43:00Z` |
| `customer_id`, `customer_name` | str | |
| `customer_tier` | str | `standard` · `business` · `enterprise` |
| `customer_region` | str | `north_america` · `europe` · `asia_pacific` · `latin_america` |
| `language_fluency` | str | `fluent` · `non_fluent` |
| `labels` | object | ground truth; **evaluation only**, never read on the runtime path |
| `history` | object | past outcomes; evaluation only |

Any field may be absent, null, blank or of the wrong type. Accepted file payloads, in this order: a top-level JSON array; a single JSON object carrying any of `ticket_id`, `channel`, `subject`, `body` (one ticket); an object with the array under `tickets`, `data` or `items`. Any other object is a `TicketFileError`, not one malformed ticket: reading `{"validation_tickets": [… 500 …]}` as a single ticket would drop 500 of them silently. The file is decoded as `utf-8-sig`, so a byte-order mark loads; anything that is not UTF-8 is a `TicketFileError`.

### Output: `Ticket` (frozen dataclass, one internal representation for all four channels)

| field | type | meaning |
|---|---|---|
| `ticket_id` | `str` | as supplied; generated deterministically when missing or blank |
| `channel` | `str` | one of the four, or `unknown` |
| `subject` | `str` | **original text, verbatim** (`""` when absent) |
| `body` | `str` | **original text, verbatim** (`""` when absent) |
| `text` | `str` | normalised subject + body: the only text downstream components read |
| `received_at` | `str \| None` | normalised `YYYY-MM-DDTHH:MM:SSZ`, `None` when missing or unparseable |
| `received_at_raw` | `Any` | as supplied (may be any JSON value, which is why it is not typed `str`) |
| `customer_id`, `customer_name` | `str \| None` | as supplied |
| `customer_tier`, `customer_region`, `language_fluency` | `str` | a known value or `unknown` |
| `defects` | `tuple[str, ...]` | machine-readable normalisation findings, sorted, deduplicated |
| `source_index` | `int \| None` | position in the input file, for reconciliation |
| `raw` | `Mapping[str, Any]` | the entry exactly as supplied, including `labels`/`history`; a read-only view, since `Ticket` is frozen and the harness scores from it |

`Ticket` deliberately has no `labels` or `history` attribute, so no runtime component can read ground truth by accident. The harness reaches `raw` for evaluation. `is_malformed` is `True` when any defect is blocking. `segments()` returns the FR-14/NFR-06 segment keys (`tier`, `region`, `fluency`, `channel`). `log_fields()` returns the ticket-side fields of a decision-log row (`ticket_id`, `channel`, `received_at`, `ingest_defects`, plus the segments), which is what FR-13 writes.

### Public functions

- `normalise_ticket(entry, *, index=None, seen_ids=None) -> Ticket` — never raises.
- `load_tickets(path) -> list[Ticket]` — one `Ticket` per input entry, in file order.
- `evaluation_labels(ticket) -> Mapping[str, Any]` — the `labels` block, for the harness only.

## 3 Decision rules, in order

1. **Entry shape.** Not a mapping (string, number, list, `null`) → a `Ticket` with defects `not_an_object` (blocking), `missing_channel`, `missing_ticket_id`, `empty_body`; `body`/`text` from the entry cleaned (a stray string still carries its words), everything else `unknown`/`None`, `raw` empty. Nothing is dropped.
2. **Identity.** `ticket_id` blank/absent → defect `missing_ticket_id` and a deterministic generated id `GEN-{index:04d}-{sha256(canonical entry)[:8]}`, or `GEN-api-{…}` when there is no file position, so an API ticket can never take row 0's id (same input → same id, NFR-08). An id already seen in this file → defect `duplicate_ticket_id`; the id is kept as supplied and the row is kept.
3. **Channel.** Absent → `unknown` + defect `missing_channel`. Present but not one of the four (case-folded, trimmed) → `unknown` + defect `unknown_channel`. Both are blocking: an unrecognised channel means the text contract is unknown, so the ticket goes to a person.
4. **Text.** `subject` and `body` are kept verbatim. `text` is built from their cleaned forms: subject then blank line then body, the subject omitted when its cleaned form already appears inside the cleaned body (5 dev tickets repeat it). Cleaning, in order: coerce to `str`; Unicode NFC; CRLF/CR → LF; delete zero-width, BiDi and other format characters (`U+200B–200F`, `U+202A–202E`, `U+2060–2064`, `U+FEFF`, category `Cf`), surrogates (`Cs`), private-use characters (`Co`) and control characters (`Cc`) except `\n` and `\t`; `\t` → space; collapse runs of spaces and of 3+ newlines; strip. Removing anything, or a CRLF line ending, records `control_characters_removed`. Longer than `MAX_TEXT_CHARS` (8000) → truncated with defect `text_truncated`; `body` still holds the whole original. `text_truncated` is not blocking here, but FR-09 routing **must escalate** on it (D-14): a ticket this far out of distribution is not one to answer from its first 8000 characters.
5. **Emptiness.** Blank `body` → defect `empty_body`. Blank `subject` → defect `missing_subject` **except on `chat`**, where the supplied data has no subject by design. Both blank, i.e. `text == ""` → defect `empty_text`, blocking: there is nothing to classify or retrieve on.
6. **Timestamp.** Accepts `...Z`, `+00:00`, a naive ISO timestamp (assumed UTC) and a space instead of `T`; normalised to `YYYY-MM-DDTHH:MM:SSZ`. A date with no time is accepted at midnight UTC with defect `imprecise_received_at`, because the time is our invention. Absent → `missing_received_at`; unparseable, or out of range once converted to UTC → `unparseable_received_at`; both give `received_at = None`. None of these is blocking: FR-05 sorts missing timestamps last.
7. **Segments.** `customer_tier`, `customer_region`, `language_fluency` outside their known sets → `unknown` plus `unknown_customer_tier` / `unknown_customer_region` / `unknown_language_fluency`. Not blocking; NFR-06 reports an `unknown` segment rather than losing the ticket.
8. **Wrong types.** A non-string value in any string field (`ticket_id`, `channel`, `subject`, `body`, `customer_*`, `language_fluency`) is coerced with `str()`, or JSON-encoded compactly if it is a list or mapping, and recorded as `coerced_field:{name}`. `null` is treated as absent, not as a coercion.

Blocking defects: `not_an_object`, `missing_channel`, `unknown_channel`, `empty_text`, `normalisation_error`.

## 4 Failure behaviour

- **Missing data, empty body, unusual characters:** never an exception. Every case above yields a `Ticket` with defects; `is_malformed` decides whether the pipeline may attempt an answer.
- **Per-entry error:** `normalise_ticket` catches anything unexpected from its own normalisation and returns a `Ticket` with defects `normalisation_error` (blocking) and `normalisation_error:{ExceptionType}` rather than propagating, so one bad ticket cannot stop a run. That ticket keeps its supplied `ticket_id` (the log must reconcile with the input file) and its `raw` (the harness must still be able to score it), `channel` becomes `unknown`, and `text` is built from the supplied `subject`/`body` only — never from a dump of the entry, which would carry `labels`/`history` onto the runtime path.
- **File-level error** (path missing or unreadable, not UTF-8, not JSON, a JSON scalar, or an object that is neither a ticket nor a recognised wrapper): `load_tickets` raises `TicketFileError`. There are no tickets to process, so this is a run failure the harness reports, not a per-ticket one.
- **Model provider error:** not reachable here. Ingest makes no model calls; it is pure and offline, which is what lets FR-15 escalate with context.
- **Invalid model output:** not applicable.

## 5 Decision-log fields

Ingest writes no log rows itself (FR-13 owns the writer, built in row 3). It supplies the fields every later row carries: `ticket_id`, `channel`, `received_at`, the `segments()` keys, and `ingest_defects` (the `defects` tuple). When `is_malformed` is true the pipeline logs, **before** replying, `decision = escalate`, `reason = malformed_ticket`, `requirement_ids = ["FR-07", "FR-09"]`, `prompt_version = null` (no model call was made), with the defect codes in the detail field.

The log's own identity is **not** `ticket_id` (author's decision, 2026-09-27, resolving question 1 below): rows are keyed on a surrogate row id, with `ticket_id` and `source_index` as columns, so a duplicate id cannot overwrite a row and reconciliation compares row count and `source_index` coverage against the input file. `Ticket.source_index` exists for exactly that.

## 6 Acceptance tests

Each is a pytest test with no network and no API key, named `test_T_FR07_n_...`. Synthetic inputs live in `tests/fixtures/malformed_tickets.json`.

1. **T-FR07-1** One ticket per channel from `data/development_tickets.json` normalises: `channel` preserved, `text` non-empty, no blocking defect, segments populated. (PRD "one ticket per channel".)
2. **T-FR07-2** Original text is kept verbatim: for a ticket whose text needs cleaning, `subject` and `body` equal the input exactly while `text` differs.
3. **T-FR07-3** An entry with only a body survives: generated id, `unknown` tier/region/fluency, the matching defects, no exception.
4. **T-FR07-4** Empty subject and empty body → `empty_text`, `is_malformed` is true, no exception.
5. **T-FR07-5** Unusual characters (zero-width, BiDi override, NUL, CRLF, combining accents, emoji, lone surrogate) are handled: no exception, `text` free of them, emoji and letters kept, defect `control_characters_removed`.
6. **T-FR07-6** Entries that are not objects (`"a string"`, `null`, `[1,2]`) each produce one malformed `Ticket` — nothing dropped.
7. **T-FR07-7** An unrecognised channel gives `channel == "unknown"`, defect `unknown_channel` and `is_malformed`.
8. **T-FR07-8** `load_tickets` on a copy of the dataset saved under an arbitrary name returns one ticket per entry, in order: tickets out == entries in.
9. **T-FR07-9** Determinism: normalising the same entry twice gives equal tickets, including the generated id (NFR-08).
10. **T-FR07-10** `Ticket` exposes no `labels` or `history` attribute, while `evaluation_labels()` returns the block for the harness.
11. **T-FR07-11** A body far over the limit is truncated in `text` with defect `text_truncated`, and `body` still holds every character.
12. **T-FR07-12** A `chat` ticket with no subject has no `missing_subject` defect and is not malformed; an `email` with no subject has the defect and is still answerable.
13. **T-FR07-13** Timestamps: `Z` form preserved; `+00:00`, naive and space-separated forms normalised; unparseable → `None` + `unparseable_received_at`; absent → `None` + `missing_received_at`.
14. **T-FR07-14** A repeated `ticket_id` in one file is kept with defect `duplicate_ticket_id` on the second row, and both rows are returned.
15. **T-FR07-15** Payload shapes: array, `{"tickets": [...]}` and a single object all load; an unreadable or non-JSON file raises `TicketFileError`.
16. **T-FR07-16** Wrong types (a number in `subject`, a list in `body`, a number in `customer_id`, `null` in `customer_tier`) are coerced, recorded as `coerced_field:{name}`, and the ticket stays answerable.
17. **T-FR07-17** All 500 development tickets load with no exception, no blocking defect, and all four channels present.
18. **T-FR07-18** A UTF-8 file with a byte-order mark loads; a file that is not UTF-8 raises `TicketFileError`.
19. **T-FR07-19** When normalisation itself fails (forced), the ticket is blocking, keeps its supplied `ticket_id` and `raw`, has `channel == "unknown"`, and its `text` holds only the supplied subject and body — no `labels`/`history`.
20. **T-FR07-20** Across every development and synthetic entry, `text` never contains a ground-truth marker (`expected_route`, `answerable_from_docs`, `must_not_auto_respond`, `first_contact_resolution`, `csat_rating`).
21. **T-FR07-21** `raw` is read-only: writing to it raises and the supplied entry is unchanged.
22. **T-FR07-22** A subject that repeats the body appears once in `text`; a distinct subject is kept.

## 7 Resolved questions

Answered by the author on 2026-09-27, after the spec was read against the PRD. Each answer is also a
`docs/decisions.md` entry, because the work it constrains belongs to later backlog rows.

- **Duplicate ticket ids → keep the supplied id, flag the row** (D-12). The decision log is keyed on a surrogate row id rather than `ticket_id`, and reconciles on row count and `source_index` coverage, so nothing has to invent an id an operator would not recognise. Neither supplied file needs this: dev and validation have 500 and 80 distinct ids with no overlap, so the rule is defensive, for the unseen file. Constrains row 3.
- **Unknown channel stays blocking** (D-13). We cannot reason about the text conventions of a channel nobody described, and a fifth channel might not be a customer at all. The cost, if the unseen file has one, is escalation rate rather than a wrong answer. Hedge: the metrics report counts `unknown_channel` tickets explicitly, so a fifth channel appears as a line in the report instead of an unexplained escalation rate. Constrains row 6.
- **The 8000-character cap stays, and `text_truncated` escalates** (D-14). The cap remains prompt safety; the escalation is the policy. A ticket ~30x longer than anything in the data (longest supplied subject+body: 276 characters) is more likely a thread dump, a log paste or an injection attempt than a question, and answering its first 8000 characters would answer half a question — the confidently-wrong failure the PRD risk register names. Ingest does **not** make `text_truncated` blocking: `is_malformed` means "no usable representation", while this is a routing policy, and the whole `body` goes to the agent in the handover. Constrains row 9.
- **`labels` and `history` stay optional, and the report says what it scored** (D-15). Absence is not a defect. The harness always computes the label-free metrics (escalation rate, citation presence, disclosure line, guardrail blocks, reconciliation, runtime, segment splits) and prints `scored against labels: N of M`, marking the accuracy sections not computable when labels are absent. `ground_truth_responses.json` is not a fallback: 200 rows, dev ticket ids only. Constrains row 6.

No FR-07 code changed as a result: all four answers are either the behaviour already specified and tested (T-FR07-7, T-FR07-10, T-FR07-11, T-FR07-8 for `source_index`) or a constraint on a later row.

# FR-02 · Escalate below a confidence threshold, and the routing decision itself

Spec written from `docs/PRD.md` FR-02 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/route.py`. This spec also defines `RoutingDecision`, which FR-09, FR-03 and FR-16 produce.

## 1 Purpose

"The system shall escalate rather than answer whenever its calibrated confidence is below a threshold T. T is chosen from development data to trade wrong answers against escalation rate, and a missing confidence counts as below T."

PRD acceptance criteria: *same ticket twice → same decision (A5). Chosen T and its trade-off curve documented. Calibration within 5 points per confidence band.* The Build Specification's "Route" section adds: a threshold "you determined from data", deterministic, and *"records the reason for the decision in language a support manager could read"*. Marcus's line in the discovery is the point — he would rather it said nothing than said something wrong.

## 2 Inputs and outputs

### Input

| name | from | used for |
|---|---|---|
| `ticket` | FR-07 | defects (`is_malformed`, `text_truncated`), id, segments |
| `classification` | FR-08 | intent, calibrated confidence, alternatives, urgency |
| `passages` | FR-10 | whether anything was retrieved |
| `extra_reasons` | FR-12 | pre-draft guardrail findings (injection, private data), slotted in by precedence |

### Output: `RoutingDecision`

| field | type | meaning |
|---|---|---|
| `decision` | `str` | `auto_respond` or `escalate` — this component never returns `block` |
| `reason` | `str \| None` | the primary reason, by D-16 precedence; `None` when answering |
| `all_reasons` | `tuple[str, ...]` | every rule that fired, in precedence order |
| `explanation` | `str` | one sentence a support manager could read (Build Spec, Route) |
| `detail` | `str \| None` | the machine evidence: matched triggers, defect codes, the intent |
| `threshold_applied` | `float` | the confidence threshold this decision was taken against |
| `confidence` | `float` | the calibrated confidence it was compared with |
| `kill_switch` | `bool` | whether FR-16's switch forced it |
| `requirement_ids` | `tuple[str, ...]` | every requirement that contributed |

`decision == "auto_respond"` is a licence to draft, not a sent reply: FR-11 drafts and FR-12's guardrails can still block, and the ticket then ends as an escalation.

## 3 Decision rules, in order

The order **is** D-16's precedence table, and it is the whole of this component:

| # | reason | requirement | condition |
|---|---|---|---|
| 1 | `kill_switch` | FR-16 | the switch is on |
| 2 | `private_data_in_ticket` | FR-12 | passed in via `extra_reasons` |
| 3 | `instruction_injection_detected` | FR-12 | passed in via `extra_reasons` |
| 4 | `malformed_ticket` | FR-07 | `ticket.is_malformed` |
| 5 | `must_escalate_intent` | FR-09 | the intent is one of the four |
| 6 | `money_commitment_requested` | FR-03 | a money trigger in the text |
| 7 | `money_decision_required` | FR-03 §3.1b | a dispute trigger in the text: the customer says a charge is wrong or not theirs. Added by review row R7 **below** the commitment rule, so every rank above keeps the place D-16 gave it |
| 8 | `date_commitment_requested` | FR-03 | a date trigger in the text |
| 9 | `compliance_data_question` | FR-09 §3.7 | the intent is `data_residency` **and** the text asks about this account's data or names a compliance, audit, legal or regulatory process. Added by review row R7 |
| 10 | `unknown_intent` | FR-09 §4 | the predicted intent is outside the 22, or there is no classification at all (D-42) |
| 11 | `text_truncated` | FR-07, D-14 | the ticket was longer than the cap |
| 12 | `no_retrieval` | FR-10 | nothing cleared the relevance threshold |
| 13 | `low_confidence` | FR-02 | calibrated confidence < T, **or absent** |

1. **Every rule is evaluated, not just the first.** `all_reasons` carries all of them so the log keeps every fact (D-16); `reason` is the highest. A short-circuit would make the log depend on evaluation order.
2. **A missing confidence counts as below T**, in the requirement's own words. `None`, a `NaN`, or a value outside `[0, 1]` is treated as 0.0 — never as high. FR-08's fallback returns 0.0 for the same reason.
3. **The comparison is `confidence < T`**, so a confidence exactly equal to T answers. That is a choice: it makes T the lowest confidence that may answer, which is the reading an operator setting `0.80` would expect.
4. **T comes from configuration** (`CONFIDENCE_THRESHOLD`), never from code, and is recorded on every decision as `threshold_applied` — FR-13 requires it on an `auto_respond` row precisely so the confidence floor is demonstrable.
5. **`extra_reasons` may only add a reason that has a rank.** An unranked name is refused, because a reason with no rank would make the primary reason depend on evaluation order — the thing D-16 exists to prevent. The names come from code, never from ticket data, so this is a programming error and is raised rather than absorbed. FR-15's `provider_unavailable` and FR-12's draft-side reasons are not routing reasons; they are recorded on their own rows.
6. **Deterministic** (NFR-08, A5): the same ticket, classification and passages always give the same decision. Nothing here reads a clock, a random number or the environment.
7. **Nothing overturns an escalation.** There is no path from `escalate` back to `auto_respond`: the function returns as soon as it has collected every reason, and a caller cannot pass a flag that ignores one.
8. **The explanation is written, not templated from codes.** Each reason has a sentence a support manager could read, because "records the reason … in language a support manager could read" is a Build Specification requirement and `low_confidence` is not language.

## 4 Failure behaviour

- **Missing data:** no classification → confidence 0.0 → `low_confidence`, and FR-09's rule 4 has already escalated it as `unclear_request`. No passages → `no_retrieval`. Both escalate; neither raises.
- **A malformed threshold** is rejected at start-up by `Settings` (outside `[0, 1]` is a `ConfigError`), so routing never compares against a nonsense number.
- **Model provider error:** routing makes no model call. A provider outage leaves routing working, which is why every ticket still reaches a logged escalation (A11, FR-15).
- **Invalid model output:** not applicable here; FR-12 handles a draft that cannot be used.

## 5 Decision-log fields

`RoutingDecision.log_fields(classification)` produces the row. It carries `prediction_confidence` — **the number routing actually compared with T**, floored at 0.0 by rule 2, not the classification's raw value, which would contradict the decision on the same row — and merges the classification's half itself, because both halves fill `detail` and splatting them side by side raises `TypeError`.

Routing writes the **terminal** row (FR-13 §3.1): `stage = "routing"`, `decision`, `reason`, `all_reasons`, `explanation`, `threshold_applied`, `prediction_value`/`prediction_confidence` from the classification, `sources_used` from retrieval, and `requirement_ids` listing every rule that fired. `prompt_version` is `null` — no model call is made to decide.

## 6 Acceptance tests

Named `test_T_FR02_n_...`.

1. **T-FR02-1** Confidence below T escalates with reason `low_confidence`; equal to T and above answers.
2. **T-FR02-2** A missing confidence, a `NaN` and a value outside `[0, 1]` each count as below T — never as high.
3. **T-FR02-3** T comes from settings and appears as `threshold_applied` on every decision, answered or escalated.
4. **T-FR02-4** The same ticket routed twice gives an identical decision, reason, `all_reasons` and explanation (A5, NFR-08).
5. **T-FR02-5** Every reason in the table produces a distinct, non-empty explanation that names no code and no field.
6. **T-FR02-6** Precedence: with several rules firing, `reason` is the highest in the table and `all_reasons` holds every one, in order.
7. **T-FR02-7** No argument or setting can turn an escalation into an answer: `Router.decide` takes no such parameter and the source contains no bypass.
8. **T-FR02-8** A decision maps onto FR-13's columns without translation, and an `auto_respond` row always carries `threshold_applied` (which FR-13 rejects a row without).
9. **T-FR02-9** Routing makes no model call and reads no clock: with a provider that raises on any call, every ticket still routes.
10. **T-FR02-10** Over the whole development set, every ticket gets a decision and no ticket gets both.

**PRD FR-02's third criterion — calibration within 5 points per band — is not tested here.** It is a property of FR-08's confidence, measured by T-FR08-18 and reported in `evaluation/reports/classifier_calibration.md`, where it **fails in one band**: 25 predictions in 0.60–0.80 state 78.6% and are right 36.0% of the time, 42.6 points out. Routing cannot fix that; it can only be honest that the number it thresholds is untrustworthy in exactly the band where the must-escalate leaks sit. `evaluation/reports/confidence_sweep.md` says so above the table, and the author decides at row 10 with that in view.

## 7 Open questions

- **T is the author's, at checkpoint row 10.** `scripts/confidence_sweep.py` writes the trade-off curve the PRD asks for; nothing here picks a value, and the placeholder 0.80 is not a recommendation.
- **The calibrated confidence spans a narrow range** (D-40): with the real embedder most predictions land between 0.8 and 1.0, so a threshold above about 0.95 escalates almost everything and one below about 0.80 escalates almost nothing. The sweep has to show that, or the choice looks freer than it is.
- **`confidence < T` versus `<= T`** matters only at the boundary, and the boundary is where a chosen threshold sits. Stated in rule 3 so the author knows which they are setting.
- **The threshold is one number for 22 intents.** A class with 60% precision and a class with 100% share it. Per-intent thresholds would be better and are a small change; they are not done because the author should see the single-threshold curve first.

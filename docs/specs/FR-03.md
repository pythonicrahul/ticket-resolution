# FR-03 · Answer explanatory billing questions, always escalate money and date commitments

Spec written from `docs/PRD.md` FR-03 with prompt PR-06 v1.0, before any code. Modules: `src/ticketing_agent/route.py` (the rule), `src/ticketing_agent/guardrails.py` (the reply-side check, shared with FR-12), `src/ticketing_agent/handover.py` (what the agent receives).

## 1 Purpose

"The system may answer explanatory billing questions (invoice lines, plans, proration, usage limits) but shall always escalate refunds, credits, disputes and any request needing a commitment about money or dates, attaching the relevant billing articles and ticket details for the agent."

PRD acceptance criteria: *engineered refund/dispute tickets always escalate. No outbound reply contains a `must_not_claim` phrase or a money/date commitment.*

The supplied data contains **zero** tickets mentioning a refund, credit, dispute or chargeback (checked: 0 of 500 development tickets match `refund|credit|dispute|chargeback|money back|reimburse`). The must-escalate half of this requirement is therefore only testable against engineered tickets, which is what backlog row 2 (B-17) builds. The 88% answerable figure in the discovery evidence refers to `billing_query`, which in this data is entirely explanatory.

## 2 Inputs and outputs

### Input

- `Ticket` (FR-07). Only `ticket.text` is examined, never `raw["labels"]`.
- The draft reply, on the way out (`str`), for the reply-side check.

### Output

`BillingDecision`, consumed by routing:

| field | type | meaning |
|---|---|---|
| `must_escalate` | `bool` | true when a money or date commitment is being asked for |
| `reason` | `str \| None` | `money_commitment_requested` · `date_commitment_requested` · `None` |
| `triggers` | `tuple[str, ...]` | the matched phrases, for the handover and the decision log |

The reply-side check returns a `GuardrailResult` (FR-12) with check name `tone_and_scope`, which is the Governance Framework's name for it (§4).

## 3 Decision rules, in order

**How a phrase is recognised (D-42).** The tables below list phrases in the singular, with spaces. Matching is case-insensitive, bounded by word edges (so `eta` does not fire inside `beta`), and additionally accepts **a plural** (`refunds`, `credits`, `disputes`, `chargebacks`, `reimbursements`) and **a hyphen where the phrase has a space** (`write-off`, `charge-back`). The literal-only version of this rule read "please issue refunds for both accounts" as an answerable billing question — the exact failure PRD FR-03 forbids — and D-21's "0 of 580 tickets match" was measured with the same literal forms, so the measurement did not cover the gap. The tables stay the source of truth for *which* phrases escalate; `route.matches_triggers` is the single implementation of how one is found in running text, and `tests/test_engineered_fixtures.py` derives the fixtures' expectations from it rather than from a second copy.

The ticket-side rule is **pure text matching, run before any model call** (NFR-07: a must-escalate ticket needs no generation call; NFR-08: the same ticket always routes the same way). It never asks a model whether something is a refund request.

1. **Money commitment requested → escalate**, reason `money_commitment_requested`. Case-insensitive, word-boundary matching on `ticket.text` against: `refund`, `refunded`, `refunding`, `credit note`, `credit back`, `account credit`, `service credit`, `sla credit`, `chargeback`, `charge back`, `dispute`, `disputing`, `disputed charge`, `money back`, `reimburse`, `reimbursement`, `compensation`, `compensate`, `waive`, `waiver`, `write off`, `cancel the charge`, `reverse the charge`, `reversal`, `goodwill`.
2. **Date commitment requested → escalate**, reason `date_commitment_requested`. Matching on: `eta`, `when will you fix`, `when will this be fixed`, `when it will be fixed`, `by when`, `firm date`, `fix date`, `delivery date`, `commit to a date`, `guarantee a date`, `deadline for the fix`, `promise`, `sla breach`. These target a commitment **we** would be making. A factual date question the documentation answers ("when does my billing period end", "how long is the retention period") matches none of them and stays answerable.
3. **Otherwise the billing question is explanatory and may be answered**, subject to every other requirement: retrieval must return something (FR-10), confidence must clear T (FR-02), the intent must not be one of the four always-escalate intents (FR-09), and the guardrails must pass (FR-12).
4. **The rule is a floor, never a ceiling.** A match escalates whatever the confidence and whatever the intent classifier said. Nothing downstream can overturn it; there is no flag, env var or configuration that switches it off.
5. **Retrieval still runs for an escalated billing ticket**, so the handover carries the relevant billing articles (`DOC-BILL-001` invoice and usage breakdown, `DOC-BILL-002` plans and proration, `DOC-BILL-003` usage limits, overage and spend controls). Generation does not run. This is the "attaching the relevant billing articles and ticket details" half of the requirement.
6. **Reply side (shared with FR-12).** Before release, the draft is checked for a money or date commitment: the three `must_not_claim` phrases that every one of the 200 ground-truth rows carries — *"a refund has been issued"*, *"the issue has been fixed on our side"*, *"a specific delivery date for a fix"* — and their close forms (`we have issued a refund`, `you will be refunded`, `we have fixed`, `this is now fixed`, `will be fixed by`, `expect a fix on`, `we guarantee`, `we promise`). A match **blocks** the reply and escalates with reason `commitment_in_draft`. The check runs on every reply, not only billing ones.

7. **Precedence.** A ticket can match this rule and another pre-model rule at once. The primary reason written to the log follows the fixed order in `docs/specs/FR-12.md` §3.4 (D-16): private data, then injection, then malformed, then FR-09 intent, then this rule. Every match is recorded in `all_reasons`, so an injection attempt that asks for a refund loses neither fact.

## 4 Failure behaviour

- **Missing or empty text:** no match, so no billing escalation; FR-07 has already flagged an empty ticket as malformed and FR-09 escalates it.
- **Empty retrieval on an escalated billing ticket:** the handover says no billing article was found. The escalation still happens; retrieval returning nothing is valid (FR-10).
- **Model provider error:** unreachable for the ticket-side rule, which makes no model call. That is the point: a refund request escalates correctly even during a provider outage (FR-15).
- **Invalid model output:** the reply-side check treats an unparseable or empty draft as a failed check and escalates. A draft that cannot be read cannot be shown to be safe.

## 5 Decision-log fields

Written **before** the action, with `requirement_ids = ["FR-03"]` (plus `"FR-09"` when an always-escalate intent also fired, `"FR-12"` for the reply-side block):

| field | value |
|---|---|
| `decision` | `escalate` |
| `reason` | `money_commitment_requested` · `date_commitment_requested` · `commitment_in_draft` · `empty_draft` (an unreadable draft cannot be shown to be safe) |
| `all_reasons` | every rule that matched, in FR-12 §3.4 precedence order |
| `detail` | the matched triggers |
| `prompt_version` | `null` for the ticket-side rule (no model call); the drafting prompt's version for a reply-side block |
| `retrieved_doc_ids` | the billing articles attached to the handover |

## 6 Acceptance tests

Named `test_T_FR03_n_...`. Tests 1, 2 and 13 are checkable at row 2 (the engineered corpus); 3 to 12 need the routing and guardrail code and belong to rows 9, 12 and 13.

1. **T-FR03-1** Every engineered money/date ticket in `tests/fixtures/` carries at least one trigger phrase from §3.1 or §3.2, is labelled `expected_route = escalate` with `must_not_auto_respond = true`, and survives ingest un-malformed (it must reach routing, not be dropped). *Row 2.*
2. **T-FR03-2** Every engineered explanatory billing ticket carries **no** trigger phrase and is labelled `expected_route = auto_respond`, so an over-broad rule fails its own fixtures. Includes the factual date question "when does my billing period end". *Row 2.*
3. **T-FR03-3** Each engineered refund, credit, dispute, chargeback and SLA-credit ticket routes to `escalate` with reason `money_commitment_requested`. *Row 9.*
4. **T-FR03-4** A ticket that asks an explanatory billing question **and then** asks for a refund escalates: the answerable first half does not rescue it. *Row 9.*
5. **T-FR03-5** "When will this be fixed, we need a firm date" escalates with reason `date_commitment_requested`; "when does my billing period end" does not escalate under FR-03. *Row 9.*
6. **T-FR03-6** The rule fires before any model call: with the provider unavailable (fake provider raising), an engineered refund ticket still escalates with the same reason, and the model-call count for it is zero. *Row 9.*
7. **T-FR03-7** An escalated billing ticket's handover contains at least one `DOC-BILL-*` article and the ticket details. *Row 13.*
8. **T-FR03-8** A draft containing any of the three `must_not_claim` phrases, or "we have issued a refund" / "this is now fixed" / "will be fixed by Friday", is blocked and escalated with reason `commitment_in_draft`, and the block is in the decision log. *Row 12.*
9. **T-FR03-9** Across a full harness run, no released reply contains a `must_not_claim` phrase or a money/date commitment. *Row 14/15.*
10. **T-FR03-10** A ticket matching both this rule and an earlier one logs the earlier reason as primary and both in `all_reasons` (FR-12 §3.4). *Row 9: covered by T-FR09-8 and T-FR02-6.*
11. **T-FR03-11** The escalation row is written to the decision log **before** the escalation is acted on, carrying `prompt_version` (`null` here, no model call) and `requirement_ids = ["FR-03"]`. *Row 9 for the row's shape (T-FR02-8: `RoutingDecision.log_fields()` maps onto a `DecisionEntry`, `prompt_version` null); row 14 for the ordering, which is `DecisionLog.perform`'s contract and is asserted where the pipeline calls it.*
12. **T-FR03-12** No keyword argument, environment variable or configuration value can switch this rule off: a search of the source finds no bypass and the routing entry point has no such parameter (§3.4). *Row 9: covered by T-FR02-7 and T-FR09-3, which scan `route.py` and `Router.decide`'s signature.*
13. **T-FR03-13** Every money and date trigger in §3.1 and §3.2 is exercised by at least one fixture, positive or `known_over_escalation`, so the over-firing question in §7 can be answered with evidence. *Row 2.*

## 7 Open questions

- **Amended (D-42): the phrases are unchanged, the matching is wider.** Plurals and hyphens now count; re-measured after the change, still **0 of the 580 supplied tickets** match any trigger, so D-21's conclusion survives its own widening. `SYN-MONEY-013` (plural) and `SYN-MONEY-014` (hyphen) are in the corpus as the regression cases.
- **Resolved (D-21): the trigger list stays as it is.** The worry was `compensation`, `waive`, `promise`, `dispute` and bare `eta` firing on ordinary prose. Measured: **0 of the 580 supplied tickets** (500 development, 80 validation) match any of the 25 money or 13 date triggers, so the over-escalation cost on this distribution is zero. The zero is also a warning — the rule is untested by real traffic, and its first live firing will be its first real test — so `SYN-MONEY-010` stays in the corpus as the honest example of what over-firing looks like. Revisit if a run produces a `money_commitment_requested` escalation on a ticket labelled `auto_respond`.
- **`eta` as a bare token.** Matched with word boundaries, so "eta" in "beta" or "theta" does not fire. An agent asking "any ETA on the docs update?" still escalates; that is `SYN-MONEY-010`, labelled `known_over_escalation` rather than hidden. Accepted under D-21.
- **Should an explanatory billing answer carry a standing disclaimer** that it is not a commitment about money? FR-06's disclosure line is separate. Not specified; raise with the author before adding text to outbound replies.
- **Urgency interaction.** A refund request from an enterprise customer escalates like any other. Whether it should also raise urgency is a business decision (the PRD leaves tier-versus-urgency to Marcus).

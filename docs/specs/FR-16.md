# FR-16 · The kill switch

Spec written from `docs/PRD.md` FR-16 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/route.py`, with the switch itself in `src/ticketing_agent/config.py`.

## 1 Purpose

"The system shall have a switch in configuration that stops all automatic replies immediately, so every ticket escalates, without a redeploy."

PRD acceptance criterion: *with the switch on, a run produces zero auto-responses and every decision records the reason.* The Governance Framework §5 asks five questions about it, and says that if you do not have one, that is your first governance finding.

## 2 Inputs and outputs

### The mechanism: a file

`KILL_SWITCH_FILE` (default `./storage/KILL_SWITCH`). **The switch is on when that file exists.** Its contents are ignored; an empty file is enough.

A file rather than an environment variable, because the requirement is "without a redeploy" and an env var needs a restart to take effect. The file is read at the moment each decision is made, so the switch takes effect on the next ticket — in a running harness, within one ticket; in the API, on the next request.

### Output

`RoutingDecision` with `decision = escalate`, `reason = kill_switch`, `kill_switch = True`, and an explanation naming the switch. Nothing else about the ticket changes: it is still classified and retrieved, so the escalation carries its handover context.

### The Governance Framework's five questions

| question | answer |
|---|---|
| What is the mechanism? | The existence of the file at `KILL_SWITCH_FILE`. `touch storage/KILL_SWITCH` turns it on; deleting the file turns it off. |
| Who is authorised to use it? | **For the author to decide and record.** Technically, anyone who can write to that directory — which is the deployment's file permissions, not this system's. |
| How long until it takes effect? | The next routing decision. There is no cache and no restart: in a harness run, the next ticket; in the API, the next request. |
| What happens to tickets in flight? | A ticket already past routing completes as it was decided. Nothing is half-sent: FR-13's row is written before the action, so the log and the outcome agree either way. At most one ticket can be answered after the switch is flipped. |
| How is it tested? | T-FR16-1 to T-FR16-6 (`tests/test_fr02_routing.py`, row 9), and a full harness run with the switch on, which must produce zero auto-responses (the PRD's own criterion). The run is T-FR16-7 and waits for row 14, when routing is wired into the pipeline; T-FR16-3 holds the same property at the router over 60 development tickets in the meantime. |

## 3 Decision rules, in order

1. **The switch is checked first**, above every other rule (D-16 rank 1). An operator turning off automation should not have to reason about what else might be true of a ticket.
2. **It forces `escalate`, never a drop.** Every ticket still gets a decision, a log row and a handover. "Stops all automatic replies" is not "stops processing".
3. **It is recorded on every decision it causes** — `reason = kill_switch`, `kill_switch = True` — because the PRD's criterion is that every decision records the reason, and because a run with a suspiciously high escalation rate must be explainable months later.
4. **It cannot be overridden.** No argument, setting or environment variable re-enables answering while the file exists. There is no `force` and no `ignore_kill_switch`.
5. **It is checked freshly each time**, not cached at start-up, which is what makes "immediately" true.
6. **A file that cannot be read** — a permissions error on the directory — counts as **on**. If we cannot tell whether automation was switched off, the safe reading is that it was.

## 4 Failure behaviour

- **Missing data:** the switch does not depend on the ticket.
- **The path does not exist:** the switch is off. That is the normal state.
- **The path exists but is a directory, or is unreadable:** on (rule 6).
- **Model provider error / empty retrieval / invalid model output:** unaffected — the switch is checked before any of them, so it works during an outage too.

## 5 Decision-log fields

`decision = escalate`, `reason = kill_switch`, `kill_switch = true` on the row, `requirement_ids = ["FR-16"]`, `prompt_version = null`. The explanation is *"Automatic replies are switched off, so this ticket goes to a person."* The harness's metrics report counts these separately so a switched-off run cannot be mistaken for a quality collapse.

## 6 Acceptance tests

Named `test_T_FR16_n_...`.

1. **T-FR16-1** With the file absent, a confident answerable ticket is auto-responded. With the file present, the same ticket escalates with reason `kill_switch`.
2. **T-FR16-2** The switch outranks every other reason: a ticket that would escalate for low confidence logs `kill_switch` as its reason and carries both in `all_reasons`.
3. **T-FR16-3** Every ticket still gets a decision and a log row with the switch on — zero auto-responses, nothing dropped (the PRD's criterion).
4. **T-FR16-4** The switch takes effect without reconstructing the router: creating the file between two `decide` calls changes the second.
5. **T-FR16-5** Nothing overrides it: `Router.decide` takes no parameter that ignores it, and the source contains no such flag.
6. **T-FR16-6** An unreadable switch path counts as on.
7. **T-FR16-7** A full harness run with the switch on produces zero auto-responses and every row carries the reason. *Row 14: the harness runs `StubPipeline` until routing is wired into the pipeline, so this test would pass for the wrong reason today.*

## 7 Open questions

- **Who is authorised to operate it** is the author's to record in the governance declaration. The system cannot enforce it; the deployment's file permissions can.
- **A file is the right mechanism here and would not be in a multi-instance deployment.** Two API processes on different machines would each need their own file. A row in the decision-log database, or a flag in a shared store, would be the production answer; the PRD's scope is a single process and the file is honest about that.
- **Nothing alerts on the switch being on.** A run whose escalation rate jumps to 100% should be noticeable, and the metrics report will show `kill_switch` as the reason, but no one is paged. Worth a line in the incident-response plan (Governance §5).
- **There is no partial switch** — no "stop answering billing tickets only". The requirement asks for all or nothing, and a per-intent switch would need its own governance.

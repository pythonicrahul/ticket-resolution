# FR-09 · The four intents that always escalate

Spec written from `docs/PRD.md` FR-09 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/route.py`, which also carries FR-02, FR-03 and FR-16 because they are one decision.

## 1 Purpose

"The system shall always escalate `security_incident`, `compliance_request`, `feature_request` and `unclear_request` by fixed rule, whatever the confidence."

PRD acceptance criterion: *zero auto-responses to tickets labelled `must_not_auto_respond` in any run.* The discovery evidence is 87 must-escalate tickets in the supplied data and both Daniel's and Ines's interviews. This is the simplest requirement in the set and the one with the least room for interpretation: four names, and no confidence, threshold, model or configuration may override them.

## 2 Inputs and outputs

### Input

- `Ticket` (FR-07) — for its defects and its id, not its text.
- `Classification` (FR-08) — the predicted intent and its confidence.

### Output

Part of `RoutingDecision` (defined in `docs/specs/FR-02.md` §2): `decision`, the primary `reason`, `all_reasons`, a manager-readable `explanation`, and `requirement_ids` including `"FR-09"`.

The reason is `must_escalate_intent`, with the intent itself in `detail`.

## 3 Decision rules, in order

1. **The four names are a constant, not configuration.** `ALWAYS_ESCALATE_INTENTS = {"security_incident", "compliance_request", "feature_request", "unclear_request"}` lives in code. There is no environment variable, argument or settings field that can shorten it — CLAUDE.md forbids a switch that turns a rule off, and this is the rule the PRD's "zero auto-responses" criterion rests on.
2. **The rule fires on the *predicted* intent**, because that is what the system knows at decision time. The label is ground truth and is never read on the runtime path (FR-07).
3. **Confidence is irrelevant.** A `security_incident` predicted at 0.31 escalates exactly as one predicted at 0.99. "Whatever the confidence" is the requirement's own wording.
4. **The fallback is one of the four.** FR-08 falls back to `unclear_request`, so a ticket that could not be classified escalates by this rule rather than by an accident of thresholds. That is why the fallback was chosen.
5. **It fires before any model call.** No draft is generated for these tickets, which is also NFR-07's "must-escalate tickets need no generation call".
6. **Precedence** is D-16's: this rule sits below the kill switch, private data, injection and malformed, and above the money and date rules. When several fire, `reason` is the highest and `all_reasons` carries them all, so a `security_incident` that also asks for a refund loses neither fact.

## 4 Failure behaviour

- **Missing data:** no classification at all escalates with reason `unknown_intent` (D-42). An earlier draft of this spec said it was "treated as `unclear_request`"; the code does not do that on purpose, because writing a prediction into the log that no model made would misreport what happened. The escalation is the same; only the reason differs, and `detail` records that the intent was absent.
- **An intent outside the 22:** escalates. An intent the system does not recognise is not one it may answer on.
- **Model provider error, empty retrieval, invalid model output:** not reachable. This rule runs before any of them, which is why it still holds during an outage (A11).

## 5 Decision-log fields

`decision = escalate`, `reason = must_escalate_intent`, `detail` naming the intent, `requirement_ids = ["FR-09"]` plus `"FR-08"` for the classification that produced it, `prompt_version = null`. The `explanation` is written for a support manager: *"This is a security report, which always goes to a person."*

## 6 Acceptance tests

Named `test_T_FR09_n_...`.

1. **T-FR09-1** Each of the four intents escalates with reason `must_escalate_intent`, at confidence 0.99 and at 0.01 alike.
2. **T-FR09-2** The other 18 intents are not escalated *by this rule* (they may escalate for another reason).
3. **T-FR09-3** No argument, settings field or environment variable shortens the list: a search of the source finds no path that removes a member, and `Router` takes no parameter that does.
4. **T-FR09-4** Zero auto-responses across the engineered corpus and the development set for tickets whose predicted intent is one of the four.
5. **T-FR09-5** The `unclear_request` fallback from FR-08 escalates by this rule.
6. **T-FR09-6** An unrecognised intent escalates.
7. **T-FR09-7** The rule fires with no model call and no retrieval: routing an always-escalate ticket touches neither.
8. **T-FR09-8** Precedence: a `security_incident` that also matches FR-03's money rule logs `must_escalate_intent` as the reason and carries both in `all_reasons`.

## 7 Open questions

- **The rule uses the predicted intent, so a misclassification can miss it.** A security incident predicted as `authentication_failure` would not escalate by this rule, though FR-02's threshold and FR-12's guardrails still stand between it and a reply. The 88.6% intent accuracy (D-39) means roughly one ticket in nine is misclassified; how many of those are must-escalate cases is a number for the sweep at row 10, and it is the strongest argument for keeping the confidence threshold conservative.
- **`feature_request` escalating is a product decision that the PRD already took** (there is no documentation to ground a roadmap answer). Worth confirming it is still wanted, since it is 20 of the 500 development tickets and they are the cheapest to answer with a templated "not on the roadmap" reply — which would need a policy, not a model.

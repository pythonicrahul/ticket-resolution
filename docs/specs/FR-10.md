# FR-10 · Retrieval from the supplied documentation, with a relevance threshold

Spec written from `docs/PRD.md` FR-10 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/retrieve.py`. The same component serves FR-04's agent search, whose acceptance test lands with the API at row 16.

## 1 Purpose

"The system shall retrieve from the 29 supplied articles only, return ranked passages with doc_id and score, and return nothing when no passage passes a relevance threshold."

PRD acceptance criteria: *every returned doc_id exists in documentation.json. Tickets with no hit are escalated, not answered.* Build Specification A4 ("the returned sources resolve back to real passages in the corpus, not to invented references") and its Retrieve section add: ranked passages **with scores**, a relevance threshold, and — the sentence worth quoting — *"chunking strategy is a decision you make, justify and are able to explain"*. §08 names the opposite failure explicitly: *"retrieval that returns something for every query regardless of relevance … always returning something hides failure."*

## 2 Inputs and outputs

### Input

- The corpus: the path in `DOCS_PATH` (`config.py`; no file name is hardcoded). Only this file is ever indexed, which is also how FR-04's "agents' private answer files shall not be indexed" is satisfied — there is no other source.
- A query: `Ticket.text` (FR-07) for the pipeline, or an agent's words for FR-04. **The query is data.** It is embedded, never interpreted, and never concatenated into anything executable.

### Output: `Passage`

| field | type | meaning |
|---|---|---|
| `chunk_id` | `str` | `DOC-BILL-001#1` — the doc id, `#`, and the chunk's ordinal within that doc |
| `doc_id` | `str` | always an id present in the corpus |
| `title` | `str` | the article title, for the citation and the handover |
| `heading` | `str` | the section this chunk came from (`Resolution`, `Symptoms`, …); empty when the article has no headings |
| `text` | `str` | the passage, as indexed |
| `score` | `float` | cosine similarity in `[0, 1]`, higher is better |
| `rank` | `int` | 1-based position in this result set |

`search()` returns a `tuple[Passage, ...]`, ordered by score descending, at most `RETRIEVAL_TOP_K`, and **empty when nothing clears the threshold**. Empty is a valid, expected answer: the documentation covers 71% of demand, so roughly three tickets in ten should retrieve nothing.

`Chunk` is the indexed unit — the `Passage` fields without a score, plus `ordinal`, `category` and `applies_to` from the document — and `resolve(chunk_id)` returns one, which is how FR-11 and FR-12 verify that a citation points at a passage that was really retrieved. `CHUNK_ID_PATTERN` describes the ids the *supplied* corpus produces; it is not enforced, because an unseen corpus may legitimately use another `doc_id` style and refusing it would lose articles for cosmetic reasons.

### Public API

- `chunk_documents(docs) -> tuple[Chunk, ...]` — pure, no Chroma, no embeddings.
- `Retriever(settings, embedder=None, client=None)` — both seams injectable, so tests never download a model or touch the network.
- `build_index(docs_path=None, rebuild=False) -> IndexStats`
- `search(query, *, top_k=None, threshold=None) -> tuple[Passage, ...]`
- `resolve(chunk_id) -> Chunk | None`

## 3 Decision rules, in order

### 3.1 Chunking, and why this way

Measured before choosing: the 29 articles are markdown with `##` sections (`Symptoms`, `Common causes`, `Resolution`, `Notes`). Split on those headings they give **145 sections, median 157 characters, longest 658, none above 800**. So:

1. **Split on markdown headings** (`MarkdownHeaderTextSplitter`, `#` and `##`, headers kept). A section is a coherent retrieval unit: a question about a symptom should match the symptom list, not half of the resolution steps.
2. **Prepend `{title} — {heading}`** to the indexed text of every chunk. The heading alone ("Resolution") means nothing in a vector space; with the title, the chunk carries what article it is from.
3. **Merge a section shorter than 120 characters into the next one.** When two merge, **the heading of the larger part survives**, because the heading is embedded with the text and would otherwise describe the smaller half. Every article opens with a title-and-"Applies to" preamble of about 76 characters, which would otherwise be a chunk that matches everything weakly and answers nothing. `applies_to` is already a field on the document, so nothing is lost.
4. **A document with no headings at all** is one chunk of its prose, with the title line and the "Applies to" line removed — the same rule as 3, not an exception to it. A document that is *only* a preamble indexes nothing.
5. **Split anything longer than 800 characters** with `RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=120)` — the pack's own Setup Guide numbers. Nothing in the supplied corpus reaches this, but an unseen corpus might, and a chunk larger than the model's useful window retrieves badly.
6. **`chunk_id = f"{doc_id}#{ordinal}"`**, ordinal 0-based over the chunks kept for that document. This is the format `tests/fixtures/draft_replies.json` already assumes, which settles the open question row 2 left for this row.

7. **Nothing is dropped in silence.** A document with no id, no content, a duplicate id, or one the splitter cannot handle is reported in `IndexStats.skipped` as `(doc_id, reason)` and logged as a warning, and `indexed_documents` says how many actually made it. A duplicated `doc_id` keeps the **first** occurrence: colliding chunk ids would otherwise abort the build and lose all 29 articles instead of one.

### 3.2 Indexing

8. **Chroma, persistent, at `CHROMA_PATH`**, one collection, **cosine** space so the score is a similarity rather than an unbounded distance. Embeddings come from Chroma's built-in all-MiniLM-L6-v2 ONNX function (D-02), which is the model the brief prescribes.
9. **The index carries a fingerprint**: `sha256` of the corpus content, the chunking rules, and the embedder **identified by its output**. `build_index()` reuses an index whose fingerprint matches and rebuilds when it does not, so a changed corpus, a changed chunking rule or a changed embedder can never be served from a stale index. Building is deterministic: chunks are added in corpus order.

  Identifying the embedder needs care, and the first version got it wrong. Chroma's default function reports the name `"default"` and an empty config, so neither distinguishes all-MiniLM-L6-v2 from whatever a future chromadb ships — a version bump would have served a persisted index built with a different model, producing meaningless similarities with no signal anywhere. So the signature embeds one fixed probe string and hashes the vector: a different model always produces a different fingerprint. The configured `EMBEDDING_MODEL` goes in too, so the id an operator set is part of the identity rather than decoration.

### 3.3 Searching

10. **Score = `1 − cosine distance`**, clamped to `[0, 1]`.
11. **The threshold is applied after ranking**: every passage scoring below `RELEVANCE_THRESHOLD` is dropped, and if that leaves nothing, nothing is returned. The threshold's **value is not chosen here** — it comes from the sweep at row 7, and until the author sets it the placeholder is 0.0, which retrieves anything. The sweep script (`scripts/retrieval_sweep.py`, writing `evaluation/reports/retrieval_sweep.md`) reports hit rate and precision across candidate values against the development tickets' `expected_doc_ids`.
12. **An empty or whitespace query returns nothing** rather than raising or matching arbitrarily.
13. **A query longer than 2000 characters is truncated**, not refused: the first 2000 characters carry the question (the longest supplied ticket is 276), and refusing would escalate a ticket for being verbose. The truncation is logged.
14. **Determinism** (NFR-08): the same query against the same index returns the same passages in the same order, because the embedder is deterministic, the index is fixed, and ties break on `chunk_id`.
15. **Every returned `doc_id` exists in the corpus.** Ids come from the index, which is built from the corpus, and `resolve()` is the check FR-11 and FR-12 use before a citation is allowed out.

## 4 Failure behaviour

- **Missing data:** a corpus file that cannot be read or parsed raises `RetrievalError` at index time — a run-level failure like `TicketFileError` (FR-07), because with no corpus nothing can be answered.
- **Empty retrieval:** not a failure. `()` is the intended answer for the 29% the documentation does not cover, and routing escalates with reason `no_retrieval` (FR-10 → D-16 rank 8).
- **A broken or unreadable index** (a corrupt Chroma directory, a failed query): `RetrievalError`, and routing escalates with reason `retrieval_unavailable`, which sits with `no_retrieval` in the precedence table. **Nothing untyped leaves this module** — the lesson from row 4's review (D-32), where an `AttributeError` from a library would have stopped the whole run instead of one ticket.
- **Model provider error:** not applicable. Embedding is local; retrieval works during a provider outage, which is part of why an outage still produces useful escalations (A11).
- **Invalid model output:** not applicable.
- **A query containing instruction-shaped text** is embedded like any other text. Retrieval cannot be steered by it, and FR-12 §3.1 has already escalated such a ticket before this point.

## 5 Decision-log fields

Retrieval writes a `continue` row (FR-13 §3.1) carrying `sources_used` — `doc_id` **with score**, as the Governance Framework's minimum record requires — plus `stage = "retrieval"`, `requirement_ids = ["FR-10"]`, `prompt_version = null` (no model call), and `threshold_applied` set to the relevance threshold, so the log shows what was asked of the retriever as well as what came back.

## 6 Acceptance tests

Named `test_T_FR10_n_...`. Offline: the corpus is the real `data/documentation.json`, the embedder is injected. Two kinds are used — a deterministic hashing embedder for behaviour, and **recorded real embeddings** (`tests/fixtures/recorded_embeddings.json`) for the semantic claims, so FR-04's criterion is a test rather than a promise.

1. **T-FR10-1** Chunking the real corpus covers all 29 documents, every `chunk_id` matches `DOC-*#n` and is unique, every chunk has non-empty text, and no chunk exceeds 800 characters.
2. **T-FR10-2** Every chunk's `doc_id` exists in the corpus, and every document's chunks are numbered from 0 with no gaps.
3. **T-FR10-3** The title-and-"Applies to" preamble is not a chunk of its own, and every indexed text opens with `{title} — {heading}`.
4. **T-FR10-4** A section longer than 800 characters is split with overlap, and the pieces keep the section's heading and the document's id.
5. **T-FR10-5** `chunk_documents` is pure and deterministic: same corpus, same chunks, in the same order, twice.
6. **T-FR10-6** The chunk ids the engineered draft fixtures cite (`DOC-BILL-001#1`, `DOC-ACCT-001#2`, `DOC-API-001#0`) all resolve, and the invented `DOC-BILL-009#0` does not — the fixtures and the retriever agree (row 2's open question).
7. **T-FR10-7** `search` returns at most `top_k` passages, ordered by score descending, each with a `rank` and a score in `[0, 1]`.
8. **T-FR10-8** With a threshold above every score, `search` returns `()` — nothing is invented to fill the gap.
9. **T-FR10-9** The threshold comes from settings when not passed, and an explicit threshold overrides it.
10. **T-FR10-10** Determinism: the same query twice gives identical `chunk_id`s, scores and order.
11. **T-FR10-11** An empty, whitespace-only or very long query returns `()` without raising.
12. **T-FR10-12** Every returned `doc_id` is in the corpus, over every development ticket's text as a query.
13. **T-FR10-13** `resolve()` returns the chunk for a retrieved id and `None` for an invented one.
14. **T-FR10-14** The index is built from the path it is given: a different corpus file yields a different index, and no file name is hardcoded.
15. **T-FR10-15** The fingerprint works: a second `build_index()` on an unchanged corpus reuses the index; a changed corpus, chunker version or embedder name rebuilds it.
16. **T-FR10-16** A corpus that cannot be read or parsed raises `RetrievalError`; a broken index raises `RetrievalError` too, never an untyped library exception.
17. **T-FR10-17** A query carrying injection markers or unusual characters returns passages or nothing, never an error, and nothing about the query changes how retrieval behaves.
18. **T-FR10-18** A passage carries what FR-13 logs: `doc_id` with `score`, ready for `sources_used`.
19. **T-FR10-19** With recorded real embeddings, "my deployment keeps dying" puts `DOC-DEPLOY-001` in the top 3 — FR-04's acceptance criterion, and the one claim a hashing embedder cannot make.
20. **T-FR10-20** With recorded real embeddings, a question the documentation does not cover scores below a covered one by a usable margin, which is what makes a threshold meaningful at all.

Added after the row 5 review:

21. **T-FR10-21** Two embedders reporting the same name and config but producing different vectors get different fingerprints — the chromadb-upgrade case the first version would have served from a stale index.
22. **T-FR10-22** A corpus with an empty document, one with no id and a duplicated id indexes what it can, reports each skip with a reason, and keeps the first occurrence of the duplicate rather than losing the whole build.
23. **T-FR10-23** A failing index query raises `RetrievalError`, never the library's own exception (D-32).
24. **T-FR10-24** When two sections merge, the heading of the larger part survives and the smaller part's text is kept.
25. **T-FR10-25** A document with no headings keeps only its prose; one that is only a preamble indexes nothing.

## 7 Open questions

- **The threshold value is the author's**, from row 7's sweep. Everything here is built so that choosing it is a one-line change in `.env` and never a code change. `Settings` now rejects a value outside `[0, 1]` and a `RETRIEVAL_TOP_K` below 1, since either would silently turn the rule off, but **no check can tell whether the placeholder 0.0 was replaced with a considered value** — and 0.0 is the "returns something for every query" mode the Build Specification §08 warns about. The metrics report at row 6 must print the threshold in use so the gate run shows it.
- **The sweep's `precision at k` has a ceiling below 100%** (70.5% on this corpus at top_k=5), because an expected article has only so many chunks. It also rises as a higher threshold returns fewer passages, which is not the same as ranking better — which is why the report carries **top-1 correct** as the column the decision actually turns on.
- **One Chroma teardown crash was observed** (`recursive_mutex lock failed` at interpreter exit) on the first full sweep, after the report had been written; a rerun exited 0 and it has not recurred. Nothing depends on the interpreter's exit code for its result, but if it reappears at row 7 it is a library teardown race, not a failure of the run.
- **Section chunking has a known weakness**: a question whose answer spans two sections (a symptom in one, the fix in another) retrieves only one of them. `RETRIEVAL_TOP_K` of 5 mitigates it, since sections of the same article score similarly, but a "parent document" strategy — retrieve the section, pass the whole article to the drafter — would handle it properly. Worth measuring at row 7 before adding the complexity.
- **Scores from a hashing embedder in tests are not comparable to real ones.** Behaviour is tested with the fake and semantics with recorded embeddings; the threshold sweep must be run with the real embedder, and the report has to say which was used.
- **The recorded-embeddings fixture is checked, not trusted.** It records the chunker version and the dimensions, and the tests assert that every current chunk is present and that the fingerprint probe is there. A missing fixture is a **failure**, not a skip: these are the only tests of FR-04's criterion, and a silent skip would delete them from a green run. What they still cannot detect is the embedding model changing while reporting the same name — the index fingerprint catches that at build time instead.
- **Non-fluent English is the fairness risk here** (NFR-06, and the Governance Framework's fairness audit says retrieval-based systems typically do worse on it). The sweep must report hit rate by fluency, not only overall, and PR-04's query rewrite exists for exactly this. Measuring it is row 7's job.

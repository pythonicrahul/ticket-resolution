# FR-11 · Draft only from retrieved passages, cite them, and say plainly when it does not know

Spec written from `docs/PRD.md` FR-11 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/generate.py`, using `prompts/build/PR-01_answer_draft_v1.0.md` and `ProviderClient.complete_structured` into `schemas.AnswerDraft` (D-31).

## 1 Purpose

"The system shall draft answers only from retrieved passages, attach citations that point to those passages, and say plainly when it does not know."

PRD acceptance criteria: *every citation resolves to a retrieved passage. Citation accuracy is at least 95% on a reviewed sample.* Build Specification A6. The discovery evidence is Ines's line about which article an answer came from, and Marcus's — he would rather it said nothing than said something wrong.

This is the first component in the system that calls a model. Everything before it (ingest, retrieval, classification, routing) is deterministic and offline; from here on, the system's output is something a model wrote, and the rules below exist to make that safe rather than to make it fluent.

## 2 Inputs and outputs

### Input

| name | from | used for |
|---|---|---|
| `ticket` | FR-07 | `channel`, `subject`, `body` — never `customer_name`, never `raw["labels"]` |
| `passages` | FR-10 | the **only** source of facts; their `chunk_id`s are the only citations allowed |
| `client` | FR-15 | `complete_structured`, temperature 0, cached |

The drafter is called **only** when routing returned `auto_respond` (FR-02). A must-escalate ticket never reaches it, which is NFR-07's "must-escalate tickets need no generation call".

### Output: `DraftResult`

| field | type | meaning |
|---|---|---|
| `usable` | `bool` | true only when a reply may be built from this draft |
| `reply` | `str \| None` | the assembled customer-facing reply (FR-06 §3 builds it), `None` when not usable |
| `draft` | `AnswerDraft \| None` | the model's parsed output, for the log and the handover |
| `reason` | `str \| None` | why it is not usable: `no_answer_drafted` · `invalid_citation` · `no_cited_article` · `empty_draft` · `malformed_draft` · `provider_unavailable` · `drafting_failed` |
| `detail` | `str \| None` | the machine evidence: the offending citation, the uncited sentence, the failure type |
| `citations` | `tuple[str, ...]` | the chunk ids the draft cites, all of them retrieved |
| `articles` | `tuple[tuple[str, str], ...]` | `(doc_id, title)` per cited article, in first-cited order, for FR-06's reply and the log |
| `prompt_version` | `str` | `PR-01 v1.0`, which FR-13 records on the row |
| `model_calls` / `cache_hits` / `latency_ms` | `int` / `int` / `float` | FR-13's per-row provider counters |
| `notes` | `tuple[str, ...]` | parser notes (unexpected fields), so prompt drift is visible |

`usable = True` is still not a sent reply: FR-12's guardrails run on it and can block (row 12).

## 3 Decision rules, in order

1. **Only retrieved passages go into the prompt.** No ticket history, no other ticket, no model knowledge invited. If `passages` is empty the drafter is not called at all — routing has already escalated with `no_retrieval` (FR-02 rank 10).
2. **Customer text is data.** The ticket goes inside `<ticket>` tags exactly as PR-01 specifies, and `<`/`>` in the ticket are replaced before insertion so a ticket cannot close the tag or open a `<passage>` one. The customer's name is never sent. Nothing from the ticket is ever concatenated into the instruction text (CLAUDE.md).
3. **One model call, with one repair attempt** — `complete_structured` (FR-15 §4) already gives exactly that, and the repair message never quotes the reply. A draft that still does not parse is `malformed_draft` and the ticket escalates.
4. **Every citation must be a chunk id that was actually retrieved for this ticket** (CLAUDE.md, and the PRD's own criterion). A citation outside that set makes the whole draft unusable — `invalid_citation` — rather than being dropped quietly. Dropping it would leave a sentence standing with no support, which is the failure this requirement exists to prevent.
   **An id written into the prose counts as a citation** (added after the row-11 review). PR-01 rule 2 shows the citation as an inline bracket, `[DOC-AUTH-001#2]`, so a model following the example literally puts the id in the sentence text — and the sentence text is what the customer reads. Checking only the `citations` array let a reply go out naming an article retrieval never returned. Both are checked; a chunk of a retrieved *article* that was not itself retrieved (`DOC-BILL-001#9`) is refused too.
5. **A sentence with no citation is sent, and the row records that it was** (D-50, the author's decision at the open question below). The reply stays the artefact the model wrote: neither refused nor edited. Nothing in this component checks whether that sentence is true, so `detail` says one went out and **FR-12's grounding guardrail (row 12) is what stands between an unsupported sentence and a customer**. A draft where *every* sentence is uncited is still refused — `no_cited_article` — because FR-06's "names the article(s) it came from" cannot be met by a reply that came from nothing.
6. **`answerable = false` is a correct outcome, not a failure.** It escalates with reason `no_answer_drafted` and carries `unknown_reason` into the handover (FR-01). Marcus's preference is the requirement: saying nothing beats saying something wrong.
7. **An empty reply is unusable** — `empty_draft`. `answerable = true` with sentences whose text is blank after assembly cannot be sent.
7a. **Nothing escapes the drafter.** `complete()` raises a bare `ValueError` when `MODEL_NAME` is blank, and a prompt file whose layout has changed raises `PromptError`; neither is a `ProviderFailure`. Both become `drafting_failed`, a logged escalation with the exception type in `detail`, because a harness catching an opaque exception cannot say in the log what went wrong (added after the row-11 review).
7b. **A prompt template this code cannot fill is refused, not sent.** `_render_user` fills the slots PR-01 declares; a later version declaring a slot it does not recognise (`Subject: {subject}` on one line) would otherwise send the literal placeholder and drop the customer's subject silently.
8. **A provider failure escalates with `provider_unavailable`** (FR-15, CLAUDE.md) and never raises past the drafter. The circuit breaker and the retries are the client's; the drafter's job is to turn a `ProviderFailure` into a logged escalation.
8a. **The row reports what the call actually cost.** `model_calls` counts every request that reached the provider, including the repair attempt and the retries behind a failure. On a free tier that column is what says whether a run fits the allowance (NFR-07).
8b. **The row names the prompt that was sent** — `Prompt.label` from the loaded file, plus its fingerprint in `notes` — not a module constant, since `Drafter(prompt=...)` can send different words.
9. **Deterministic** (NFR-08): temperature 0 and the response cache, so the same ticket and the same passages give the same draft. The prompt is built in a fixed order — passages in retrieval rank order — because reordering them would change the cache key and the reply.
10. **The model never writes the disclosure or the greeting.** FR-06 §3 assembles those in code, so an automated reply cannot lose its disclosure to a model's paraphrase.

## 4 Failure behaviour

- **Missing data:** no passages → the drafter is not called (routing escalated). No ticket text → FR-07 flagged it malformed and routing escalated. Neither reaches here.
- **Empty retrieval:** as above. Returning nothing is valid (FR-10) and is an escalation, never an invented answer.
- **Model provider error:** `provider_unavailable`, logged, the ticket escalates, the run continues (A11, CLAUDE.md's "one ticket failing must never stop a run").
- **Invalid model output:** `malformed_draft` after `complete_structured`'s repair attempt. A half-understood answer is never passed downstream.
- **A draft that cites an article that exists but was not retrieved for this ticket:** `invalid_citation`. The chunk id looking well-formed is not the test; being in this ticket's retrieval is.

## 5 Decision-log fields

Stage `generation`, written **before** the reply is sent (FR-13): `decision` (`continue` when usable, `escalate` when not), `reason`, `detail`, `citations`, `retrieved_doc_ids`, `prompt_version = "PR-01 v1.0"`, `model_name`, `model_calls`, `cache_hits`, `latency_ms`, `requirement_ids = ["FR-11"]` plus `["FR-06"]` for the assembled reply and `["FR-15"]` for a provider failure. The draft text itself is **not** logged in full: FR-13 caps and scrubs free text, and the reply is the artefact, not the log.

3. **T-FR11-3** A draft citing a chunk id that was **not** retrieved is unusable with reason `invalid_citation`, and no reply is produced — the citation is not dropped to rescue the sentence.
4. **T-FR11-4** A draft with a sentence carrying no citation is **sent**, the sentence unchanged, and the row's `detail` records that it went out (D-50). **T-FR11-4b** a draft citing nothing at all is refused with `no_cited_article`.

7. **T-FR11-7** A `ProviderFailure` becomes `provider_unavailable` with no exception escaping the drafter.

9. **T-FR11-9** A ticket whose body contains `</ticket>`, `<passage id="X">` or other tag look-alikes cannot break out of its tags: the assembled prompt still has exactly one `<ticket>` element and no injected `<passage>` element.

## 7 Open questions

- **Resolved (D-50): an uncited sentence is sent.** The author chose this over refusing the draft or dropping the sentence, on the grounds that the reply should be what the model wrote. The cost is explicit: an unsupported sentence can reach a customer, and only FR-12's grounding check stands in its way. Revisit if row 12's guardrail turns out to let unsupported sentences through, or if a reviewed sample shows the uncited sentences are where the wrong answers are.
- **Citation granularity.** Citations are chunk ids (`DOC-BILL-001#2`); the customer-facing reply names the article (`DOC-BILL-001`), since a chunk ordinal means nothing to a customer. The decision log keeps the chunk id, which is what makes the citation checkable.
- **No sentence-level grounding check here.** Whether a cited passage actually *supports* the sentence is FR-12's grounding guardrail (PR-03, row 12). This component only enforces that a citation exists and points at something retrieved.
- **`empty_draft` and the "no article to name" lock are unreachable today.** `schemas` already rejects a blank sentence and an answerable draft with no sentences. Both checks stay as second locks, because the schema is one edit away from allowing what they catch, and an empty or unsourced reply must never be sendable.
- **Inline ids are validated but not rewritten.** A reply may therefore read `… [DOC-BILL-001#2].` with the chunk ordinal visible to the customer, next to a `Based on:` line naming the article. Tidying that means editing the model's words, which FR-06 §3 deliberately does not do — worth the author's decision.
- **Reply length and tone are the model's**, bounded by PR-01's "under 150 words". Nothing here measures tone; PR-05's judge does, at the evaluation stage.

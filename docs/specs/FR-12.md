# FR-12 · Guardrails on every draft: private data, grounding, instruction integrity, commitments

Spec written from `docs/PRD.md` FR-12 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/guardrails.py`, called from `src/ticketing_agent/pipeline.py`.

## 1 Purpose

"The system shall run guardrails on every draft before release (private data, grounding, instruction integrity, commitments), and any failure shall block the reply and escalate."

PRD acceptance criteria: *engineered PII, injection and commitment tickets are each blocked. The block is recorded in the decision log.* NFR-04 adds: **zero** private data in outbound replies, and the guardrail **blocks, it does not redact**.

The Governance Framework (`Capstone_Pack/03_Reference/Governance_Framework.docx` §4) names **five** guardrails, and its wording sets the vocabulary this spec uses: *"A guardrail is a check that runs on every response and can block it. Guardrails that only run in testing are not guardrails; they are tests."* Build Specification A7 is the criterion — a ticket engineered to trigger it is submitted and the response must be blocked rather than sent — and its "Validate" section adds that the check "records what it checked and what it found, whether or not it blocked".

## 2 Inputs and outputs

### Input

| name | type | notes |
|---|---|---|
| `ticket` | `Ticket` (FR-07) | customer text, always treated as data |
| `draft` | `str \| None` | the candidate reply; `None` or empty is itself a failure |
| `retrieved` | `tuple[Passage, ...]` | what retrieval returned (FR-10): chunk id, doc_id, text, score |
| `citations` | `tuple[str, ...]` | the chunk ids the draft cites |

Engineered inputs for all of this live in `tests/fixtures/`: tickets in `pii_tickets.json`, `injection_tickets.json` and `money_commitment_tickets.json`, and drafts with their retrieved passages in `draft_replies.json`, so every post-draft check can be tested offline with no model call.

### Output

`GuardrailReport`:

| field | type | meaning |
|---|---|---|
| `passed` | `bool` | true only when every check passed |
| `results` | `tuple[GuardrailResult, ...]` | one per check, always all five, in fixed order |
| `blocking` | `tuple[str, ...]` | names of the checks that failed |
| `reason` | `str \| None` | the decision-log reason for the first failure |

`GuardrailResult`: `name`, `passed`, `detail` (the matched phrase, the unsupported sentence, the unresolvable citation), `requirement_ids`. The five names are the Governance Framework's own:

| name | framework's row | what it checks | what happens when it fires |
|---|---|---|---|
| `private_data` | Private data | names, addresses, keys, account numbers, anything identifying another customer | block and escalate, never redact and send |
| `grounding` | Grounding | every factual claim traceable to a retrieved passage | block and escalate with the unsupported claim flagged |
| `instruction_integrity` | Instruction integrity | the ticket content has not altered the system's instructions | block, escalate and record the input for review |
| `tone_and_scope` | Tone and scope | the reply stays in support scope and makes no commitment about money or dates | block; commitments are not the system's to make (shared with FR-03) |
| `confidence_floor` | Confidence floor | the routing threshold was actually applied, and a missing confidence is not a high one | escalate, with `threshold_applied` recorded (FR-02, FR-13) |

## 3 Decision rules, in order

Two stages. **Pre-draft rules** run on the ticket before any model call, so a hostile or PII-bearing ticket costs nothing and no draft is ever created (NFR-07). **Post-draft checks** run on every draft without exception.

### 3.1 Pre-draft, on the ticket

1. **Instruction integrity.** Case-insensitive matching on `ticket.text` for instruction-shaped text: `ignore all previous`, `ignore previous instruction`, `ignore the above`, `ignore your instruction`, `disregard your`, `disregard all previous`, `disregard the above`, `you are now`, `pretend to be`, `new instructions`, `system:`, `assistant:`, `</ticket>`, `<ticket>`, `reveal your`, `show me your prompt`, `system prompt`, `repeat your instructions`, `your instructions verbatim`, `developer mode`, `jailbreak`, `bypass your`. A match escalates with reason `instruction_injection_detected`, before any model call.

  `system:` and `assistant:` match **only at the start of a line** (after optional whitespace or a `>` quote marker). A role label at a line start is what an injected transcript looks like; the same words inline ("restart requested by system: worker-3", a pasted log) are ordinary customer prose. Measured on the supplied data: neither label appears in any of the 580 tickets, so the anchoring costs nothing today and removes the one marker most likely to over-fire on a log paste. `SYN-INJ-007` carries a line-start label and `SYN-INJ-LOOKALIKE-003` an inline one.

  Every other marker is a **phrase**, not a bare word. The first draft of this list carried `override`, `act as` and `your guidelines`, which match ordinary support questions ("how do I override the default retry interval", "can a webhook act as a health check"). Those questions are in the corpus as `injection_lookalike` fixtures, and they are why the list is phrases: escalating them would cost first-contact resolution with no safety gained, since customer text is already confined to `<ticket>` tags and multi-word markers still catch the engineered attacks.
2. **Private data in the ticket.** Only **high-risk secrets** escalate pre-draft, because they must never be embedded, cached or sent to a provider: a card number (13–19 digits, Luhn-valid, separators ignored), a national-insurance/social-security-shaped number, a password or credential assignment (`password:`, `passwd=`, `secret:`, `token=`, `api_key=`, `private key`, `BEGIN … PRIVATE KEY`). Reason `private_data_in_ticket`. A customer's own email address or phone number does **not** escalate on its own — it is normal in a support ticket — but it must not appear in the reply, which §3.2 enforces.

Customer text stays inside `<ticket>` tags and is never concatenated into instructions, so these rules are defence in depth, not the only protection.

### 3.2 Post-draft, on the draft, in this order

1. **`private_data`.** Block if the draft contains: an email address, a phone number (7+ digits with separators), a Luhn-valid card number, a national-id-shaped number, a credential assignment, an API-key-shaped token (16+ chars of mixed case and digits after a `key`/`token`/`secret` label), or a private IP address. Block, never redact (NFR-04). Detail names the pattern, **never the matched value**, so the decision log cannot become the leak.
2. **`grounding`.** Deterministic like everything else that can change a routing decision: the PR-03 call is temperature 0, its prompt version is pinned and written to the log, and responses are cached, so the same draft always gets the same verdict (NFR-08, NFR-07). Every citation must be a chunk id in `retrieved` (FR-11). A draft citing nothing while making claims fails. A draft that says plainly it does not know, with no claims, passes.

  **What counts as a claim.** Defining this comes before any threshold, because getting it wrong makes every threshold unusable. A sentence is exempt — it asserts nothing about the product and needs no support — when it is a greeting, an apology, an offer to follow up, an instruction to reply, or the FR-06 disclosure line; concretely, when it opens with `thank`, `thanks`, `welcome`, `apolog`, `i hope`, `glad`, `happy to`, `please reply`, `do let me know`, `let me know`, `i would suggest starting`, `if you work through`, `based on what you have described`, or is the disclosure sentence. Everything else is claim-bearing and must be supported.

  **Support threshold: 0.3** of a claim-bearing sentence's content words (stopwords removed, case-folded) must appear in a cited passage, alongside the PR-03 judgement. Measured against the 200 expert reference answers and the articles they cite: of 997 sentences, 351 are exempt pleasantries, and of the 646 genuine claims, a threshold of 0.3 rejects 3.6%, 0.4 rejects 6.7% and 0.5 rejects 19.3% (p1 0.25, p5 0.33, median 0.70). Applying a threshold without the exemptions above would reject 37–48% of what CloudServe's own senior agents wrote. The overlap check is a cheap floor against invention; the hallucination budget of NFR-03 (≤5%) rests on the PR-03 judgement, not on word counting.

  **This number is provisional** (D-22): it was measured against whole articles, while retrieval will supply narrower chunks, so row 5 must measure it again on real chunks and the author confirms or changes it then.
3. **`instruction_integrity`.** Reason `instruction_leak_in_draft`. Block if the draft echoes prompt or system text, contains `system prompt`, `my instructions`, `as an AI`, or repeats an injection marker from §3.1 — evidence the draft followed the ticket rather than the instructions.
4. **`tone_and_scope`.** Block if the draft contains a money or date commitment: the three `must_not_claim` phrases carried by all 200 ground-truth rows — **"a refund has been issued"**, **"the issue has been fixed on our side"**, **"a specific delivery date for a fix"** — and their close forms (`we have issued a refund`, `a refund will be issued`, `you will be refunded`, `we have fixed`, `this is now fixed`, `will be fixed by`, `expect a fix on`, `we guarantee`, `we promise`, `we commit to`). Shared with FR-03 §3.6. The framework calls this row "Tone and scope"; commitments are its core, and scope creep beyond support is the rest.

5. **`confidence_floor`.** Block if the routing threshold was not applied, or was applied to a missing confidence. The framework is explicit that "a missing confidence score is not a high one", which is also FR-02's rule. The check reads the `threshold_applied` and confidence that FR-13 requires on an `auto_respond` row, so a reply cannot be released without evidence that the floor was enforced.

### 3.3 Invariants

- All five checks run on **every** draft. No flag, environment variable, configuration value or `except` clause may skip one. There is no `disable_guardrails`, no `strict=False`, no test-only bypass; the tests exercise the real checks.
- Any failure **blocks the reply and escalates**. Blocking is the only outcome: nothing is redacted, rewritten or retried into compliance.
- A check that raises is a **failure**, not a pass: the exception is caught, the result is `passed = False` with detail `check_error:{Type}`, and the ticket escalates. A guardrail that cannot run has not cleared the reply.
- The block is written to the decision log **before** the escalation is acted on (FR-13).

### 3.4 Precedence among the pre-model escalation rules

Several rules can fire on one ticket (`SYN-INJ-001` is an injection attempt *and* a refund request). The
decision log therefore records **`reason`**, the single primary reason, and **`all_reasons`**, every rule
that matched in this order. The order is fixed, so the same ticket always logs the same primary reason
whatever order the code happens to evaluate in (NFR-08, FR-13). Decided as D-16.

| rank | reason | requirement | why it outranks the rest |
|---|---|---|---|
| 1 | `kill_switch` | FR-16 | an operator has turned automation off; nothing may override that |
| 2 | `private_data_in_ticket` | FR-12 | a secret must not be embedded, cached or sent anywhere, so this decision is taken before the text is read for anything else |
| 3 | `instruction_injection_detected` | FR-12 | the text is hostile, so no other reading of it is trustworthy |
| 4 | `malformed_ticket` | FR-07 | there is no usable representation to classify or retrieve on |
| 5 | `must_escalate_intent` | FR-09 | the class is never automatable, whatever the confidence |
| 6 | `money_commitment_requested`, then `date_commitment_requested` | FR-03 | a contractual commitment about money or a date |
| 7 | `text_truncated` | FR-07, D-14 | far out of distribution (D-14) |
| 8 | `no_retrieval` | FR-10 | nothing to ground an answer in |
| 9 | `low_confidence` | FR-02 | below the threshold T |

Post-draft reasons (`private_data_in_draft`, `ungrounded_draft`, `commitment_in_draft`, `empty_draft`,
`check_error`, `provider_unavailable`) can only arise when no rule above fired, since otherwise no draft
was made; among themselves they are ordered by the check order of §3.2.

## 4 Failure behaviour

- **Missing data:** `draft` `None` or blank → `commitments` and `grounding` cannot be satisfied → block, reason `empty_draft`.
- **Empty retrieval:** a draft with any claim fails `grounding`; there is nothing to ground it in. This is the intended path for the 29% of tickets the documentation cannot answer.
- **Model provider error** (PR-03 unavailable for the grounding judgement): the deterministic exact-quote check still runs, and an unavailable judge counts as a failed check, so the ticket escalates with reason `provider_unavailable` (FR-15). A reply is never released on the strength of a judge that did not answer.
- **Invalid model output** (PR-03 returns unparseable JSON): treated as a failed check, not as a pass.

## 5 Decision-log fields

| field | value |
|---|---|
| `decision` | `escalate` (a guardrail never produces a send) |
| `reason` | the primary reason by §3.4 precedence: `instruction_injection_detected` · `private_data_in_ticket` · `private_data_in_draft` · `ungrounded_draft` · `instruction_leak_in_draft` · `commitment_in_draft` · `threshold_not_applied` · `empty_draft` · `check_error` · `provider_unavailable` |
| `decision` | `block` for the blocked reply (the framework's third `action_taken`), then `escalate` as the ticket's terminal row (FR-13 §3.1) |
| `all_reasons` | every rule that matched, in §3.4 precedence order, so a ticket that is both an injection attempt and a refund request loses neither fact |
| `detail` | the pattern name and, for grounding, the unsupported sentence. Never the matched private value. |
| `guardrail_results` | all four check names with pass/fail, so the log shows the ones that passed too |
| `prompt_version` | `PR-03 v1.0` when the grounding judge ran; `null` for a pre-draft rule |
| `requirement_ids` | `["FR-12"]`, plus `["FR-11"]` for grounding, `["FR-03"]` for commitments, `["NFR-04"]` for private data |

## 6 Acceptance tests

Named `test_T_FR12_n_...`, and the list numbers are the test numbers. Tests 1 to 5, 17, 21, 22 and 23 are checkable at row 2 (the engineered corpus and this spec's own consistency with the data); 6 to 16, 18 and 19 need the guardrail code (row 12), and 20 needs the drafting prompt (row 11).

2. **T-FR12-2** Every engineered ticket survives ingest (FR-07) without raising, and the PII, injection and money tickets are **not** malformed — they must reach the guardrails rather than be dropped earlier. *Row 2.*

4. **T-FR12-4** Every `injection` fixture contains at least one marker from §3.1.1, and every `injection_lookalike` contains none, so an over-broad detector fails its own fixtures. *Row 2.*
5. **T-FR12-5** Every `must_not_claim` phrase in the supplied ground-truth file appears verbatim in this spec's commitment list, and the pattern tables mirrored in the tests match this spec's tables **in both directions**, so neither the guardrail nor the mirror can drift from what the data demands. *Row 2.*
6. **T-FR12-6** An engineered injection ticket escalates with reason `instruction_injection_detected` and zero model calls. *Row 12.*
7. **T-FR12-7** A ticket carrying a card number or a credential escalates with reason `private_data_in_ticket`, and no provider call is made with that text. *Row 12.*
8. **T-FR12-8** A draft containing an email address, phone number or card number is blocked with reason `private_data_in_draft`, and the reply is **not** sent in redacted form. *Row 12.*
9. **T-FR12-9** The decision-log detail for a private-data block names the pattern and does **not** contain the matched value. *Row 12.*
10. **T-FR12-10** A draft citing a chunk id that was not retrieved fails `grounding`. *Row 12.*
11. **T-FR12-11** A draft asserting a fact absent from the retrieved passages fails `grounding`; a draft that says it does not know passes. *Row 12.*
12. **T-FR12-12** A draft containing each of the three `must_not_claim` phrases is blocked with reason `commitment_in_draft`. *Row 12.*
13. **T-FR12-13** All five results are present, in fixed order, on every report, pass or fail, and each records what it checked whether or not it blocked (Build Specification, Validate). *Row 12.*
14. **T-FR12-14** A check that raises yields `passed = False`, detail `check_error:{Type}`, and an escalation — never a pass. *Row 12.*
15. **T-FR12-15** The grounding judge being unavailable blocks the reply (reason `provider_unavailable`); the deterministic quote check still ran. *Row 12.*

18. **T-FR12-18** The block is written to the decision log **before** the escalation is acted on, and the row carries `prompt_version` and `requirement_ids`: with a recording log writer, the log call precedes the escalation side effect and exactly one row is written per block. ## 7 Open questions

- **Partly resolved (D-22): the grounding threshold is 0.3, provisionally, and the exemption list is the substantive half.** See §3.2.2 for the measurement. It was set from development data on the author's instruction rather than chosen by the author, and it was measured against whole articles rather than the chunks retrieval will return, so row 5 re-measures on real chunks and the author confirms the number then. The exemption list (what counts as a claim) is the part that makes any threshold workable and should be reviewed on its own.
- **Resolved (D-24): `system:` and `assistant:` are kept, anchored to the start of a line.** A role label at a line start is what an injected transcript looks like; the same words inline are ordinary prose, including a pasted log. Neither label appears in any of the 580 supplied tickets, so the anchoring has no measured cost and removes the one plausible false positive. `SYN-INJ-007` (line start, escalates) and `SYN-INJ-LOOKALIKE-003` (inline, must not) hold both halves.
- **Private IP addresses as private data.** `10.0.0.5` is not personal data, but repeating a customer's internal topology in a reply is poor practice. Included in the draft-side list; remove if it proves noisy.
- **Resolved (D-23): a customer's own email in a reply is still a leak.** NFR-04's "zero private data in outbound replies" is read strictly — blocked even when the customer supplied the address, because the reply may be seen by others on the account. Measured: **0 of the 200 expert reference answers** contain an email address or phone number, so the strict reading is exactly what CloudServe's senior agents already do, and 0 of 580 tickets contain an address either, so it costs nothing on this data. `SYN-PII-003` is the only fixture that exercises it.
- **Where the pattern tables live.** They are in this spec now, and the tests at row 2 mirror them to check the fixtures. Row 12 must implement them in `guardrails.py` as the single source of truth and point the tests at that module, deleting the mirrored copy.

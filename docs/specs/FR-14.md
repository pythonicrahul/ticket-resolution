# FR-14 · The evaluation harness: one unattended run, one metrics report

Spec written from `docs/PRD.md` FR-14 with prompt PR-06 v1.0, before any code. Modules: `evaluation/harness.py`, with the per-ticket contract in `src/ticketing_agent/pipeline.py`.

## 1 Purpose

"The system shall process any ticket file given by input and output paths in one unattended run and produce a metrics report, including every metric split by tier, fluency, region and channel."

PRD acceptance criteria: *harness runs on the 80 validation tickets and on an unseen file with no intervention; the report appears automatically.* This is the row the whole project turns on. The Build Specification is blunt about it: A9 ("started once and left alone — no manual intervention, no restarts, no skipped tickets; then re-run against a file you have never seen"), A10 ("that run produces a metrics report without further manual work"), and §04 ("your harness must accept an input path rather than a hardcoded filename, because it will be pointed at that file after you submit"). §08 lists the ways this fails: a notebook, a demonstration on five hand-picked tickets, a decision log written only for the tickets that succeeded.

## 2 Inputs and outputs

### Command

    uv run python -m evaluation.harness --input PATH --output DIR

`--input` and `--output` are the only required arguments and **nothing about either is hardcoded** (CLAUDE.md's first non-negotiable). Optional: `--docs`, `--decision-log`, `--run-id`, `--limit` (for a smoke run; never used for a reported figure), `--no-index-rebuild`, `--stub-pipeline` (exercises the machinery with no model; a gate run must not use it), `--no-cache` (added by review row R5: a timing run, which neither reads nor writes recorded provider responses — it cannot reproduce itself, so it is not the run to show for A5 or NFR-08, and the report records that reads were off).

### Output, written to `DIR`

| file | what it is |
|---|---|
| `metrics.json` | every figure, machine-readable, for the report and for a diff between runs |
| `metrics.md` | the same figures as the report a human reads, in the Build Spec §04 groups |
| `outcomes.jsonl` | one line per ticket: its decision, reason, passages, timing — the audit trail beside the decision log |

The decision log is written to `DECISION_LOG_PATH` (FR-13), not into the output directory, because it is runtime state that outlives one run.

### The per-ticket contract (`pipeline.py`)

`Pipeline.process(ticket) -> Outcome`. `Outcome` carries the decision (`auto_respond` · `escalate` · `block`), the machine `reason`, the human `explanation`, `all_reasons`, the passages retrieved, any draft and its citations, the guardrail results, `threshold_applied`, the prediction and its confidence, the handover `summary`/`uncertainty`, and the model-call counters. Those are exactly FR-13's columns, so the harness never has to invent a field.

**Row 6 ships a stub pipeline**, because classification, drafting, guardrails and routing are rows 8 to 13. The stub is not a placeholder that returns nothing: it runs the parts that exist — FR-07 ingest and FR-10 retrieval — and escalates with an honest reason. That makes the harness end-to-end **today**: every ticket is processed, every decision is logged, reconciliation is real, and retrieval hit rate is measured. Row 14 replaces the stub with the LangGraph pipeline and nothing in the harness changes.

## 3 Decision rules, in order

1. **Read the input file through FR-07.** `load_tickets` gives one `Ticket` per entry, so tickets out always equals entries in. A file-level failure (`TicketFileError`) ends the run with a non-zero exit and a message naming the path: there is nothing to process.
2. **Start the run in the decision log** (`start_run`), recording the input path and the ticket count, so the log can be reconciled later from the database alone (FR-13 §3.4).
3. **Process each ticket in isolation.** The guard covers **the whole of one ticket's handling**, not just the pipeline call: the outcome may be the wrong type, or valid Python but invalid for the log (an escalation with no reason, an unknown stage, an `auto_respond` with no `threshold_applied`). Any of those becomes an escalation with reason `pipeline_error`, a logged row, and the next ticket. This is the rule A9 tests and CLAUDE.md states twice.

  The distinction that matters, and that the first version got wrong: an **invalid call** about one ticket is that ticket's failure, while a **log that cannot be written at all** is the run's (D-27). `InvalidDecision` is caught per ticket; only `DecisionLogUnavailable` stops the run. Conflating them reported a component's bug as an unwritable log and abandoned every remaining ticket — with 76 of 80 never attempted, which is the failure §08 lists.

  `detail` carries the exception type, and its message only when the message cannot be quoting the customer: a parse or provider error can echo the payload it choked on, and `detail` reaches the decision log (NFR-04). Any message containing a run of the ticket's own words is withheld.
4. **Check the output directory before processing a single ticket.** Discovering a mistyped or unwritable `--output` after 80 tickets throws the whole run away, and A10 is that the report appears without further work. The directory is created and probed first, and a failure is a `HarnessError` with a message, not a traceback. The report writing itself is wrapped too: a run that happened must not be lost to a formatting error.
5. **Log before acting** (FR-13): the outcome's row is written through `DecisionLog.perform`, and only then is the answer "sent" (recorded in `outcomes.jsonl`). A decision that cannot be logged fails the run rather than proceeding unlogged (D-27), because that breaks FR-13 for every ticket, not one.
6. **Reconcile** (`DecisionLog.reconcile`) after the last ticket, and put the result in both reports. `ok` false is a **run failure**: the log and the tickets disagree, which is precisely what A8 checks.
7. **Score against labels when they are there** (D-15). `evaluation_labels()` is the only way ground truth is read. Every label-free figure is always computed; the accuracy figures are computed for the tickets that have labels, and both reports state `scored against labels: N of M`. A file with no labels produces a complete report with the accuracy sections marked not computable — never a crash and never a silently smaller denominator.
8. **Never tune on this.** The harness reports; it does not choose. `--limit` exists for a smoke run and is recorded in the report when used, so a truncated run cannot be mistaken for a full one.
9. **Exit code**: 0 when every ticket was processed and reconciliation passed; 1 when the run could not start or reconciliation failed. A ticket that escalated is not a failure — escalation is a correct outcome.

## 4 What the report must contain

The Build Specification §04 names four groups and requires them to be "calculated by your code rather than by hand afterwards". All four are mandatory:

| group | figures |
|---|---|
| **Volume** | tickets processed, answered automatically, escalated, **blocked by guardrails** |
| **Business** | first contact resolution, **mean and median** response time, escalation rate |
| **Technical** | classification precision **and recall per class**, retrieval hit rate, latency at **median and p95** |
| **Governance** | decisions logged, guardrail activations **by type**, private data detections |

Plus, from the other two pack documents:

- **The Evaluation Framework's results table**: measure, baseline, target, achieved, confidence in the figure, notes. The baselines and targets are the pack's (FCR 42% → 60%, reply time 8–12 h → under 5 min, escalation 58% → ≤30%, precision ≥85%, hallucination ≤5%, citation accuracy ≥95%, latency p95 < 3 s, private data 0, cross-group variation < 5 points).
- **Segment tables** for every metric, by **tier, fluency, region, channel** (NFR-06) **and a short/long ticket band** — the Governance Framework's fairness audit names ticket length and the PRD's four segments do not. Each row carries its sample size, and segments below 10 tickets are flagged low confidence (the validation set has 8 enterprise tickets).
- **The thresholds in use** — relevance and confidence — printed in both reports, so a gate run shows whether the placeholders were ever replaced (FR-10 §7).
- **Honest gaps.** A figure the system cannot produce yet says so by name. A report that quietly omits hallucination rate reads as though it were zero. Three figures in particular carry their own caveat next to the number, because they are the eye-catching ones and each is easy to over-read:
  - **Route agreement** is agreement with the labelled `expected_route`. ~~While the answering path is unbuilt every ticket escalates, so the figure is simply the share of tickets labelled escalate.~~ It does not measure routing, and the report says so. **Amended by review row R4:** the caveat is now conditional on *the run*, not on the build. When nothing was answered the old sentence is printed verbatim (it is then true); when both outcomes occur the report prints the share this run escalated beside the share labelled escalate, so a reader can see how much of the figure is the base rate. A binary "this is a real comparison" was rejected because it flips at the first answered ticket, and 79 of 80 escalations is still a base rate.
  - **Escalation rate and the FCR proxy**: ~~100% escalation before row 14 is **by construction**. The gaps list says this in those words~~. **Amended by review row R4:** "by construction" was a constant naming build rows 8 to 13, and it was still printed after they were built. The report now says *why this run* escalated everything, and only claims a construction when one is identifiable: a stub run, the kill switch (FR-16), or every ticket escalating on a rule or a failure rather than on the threshold. A run where the threshold did the work says so instead. The phrase is therefore no longer mandated "in those words", and `T-FR14-25` asserts the property rather than the wording.
  - **Retrieval hit rate** counts labelled-answerable tickets only, at the threshold in use, so it has no false-positive counterpart and cannot fall when retrieval returns too much.
- **A fairness figure that can only say "pass" is not a measurement.** `variation_points` is computed over **every** segment that has tickets — excluding the small ones would drop the 8 enterprise tickets NFR-06 names and understate the gap — and is `null` with "not measurable" when fewer than two segments exist, rather than `0.0`. Small segments are listed beside the figure. The markdown states whether the variation is within or **above** the 5-point limit.
- **Segments carry a quality figure, not only a rate.** NFR-06 is about resolution rate *and quality*, so retrieval hit rate is segmented too: a retrieval gap on non-fluent tickets is the one the Governance fairness audit predicts and the one the PRD's Stage 1 disagreement is about.
- **`unknown_channel` gets its own line** (D-13), with the full ingest-defect breakdown beside it, so a fifth channel appears as a number rather than hiding inside `malformed_ticket`.

## 5 Decision-log fields

The harness writes no ticket decisions of its own; the pipeline's outcome becomes the row. It writes the two run rows (`start_run`, `finish_run`) and, for a ticket that raised, the `pipeline_error` escalation with `requirement_ids = ["FR-14", "FR-15"]` where the cause was a provider failure, `["FR-14"]` otherwise.

## 7 Open questions

- **"First contact resolution" cannot be observed offline.** The PRD says so and this report must repeat it: what is measured is the share of tickets answered automatically and not escalated, which is *correct automated handling*, not a confirmed resolution. The label `first_contact_resolution` in the data is the historic human outcome, not ours.
- **Response time is not measurable either.** There is no first-reply timestamp in the data, so the only honest figure is the harness's own processing time per ticket. The report says that plainly rather than printing a number that looks like a customer-visible wait.
- **Hallucination rate and citation accuracy need human review** (the Evaluation Framework asks for two assessors over ≥50 responses). The harness can count citations that fail to resolve, which is a floor, not the rate. Both are marked as requiring review.
- **The stub pipeline's escalation reason** is `pipeline_incomplete` until row 14. Every run before then will show a 100% escalation rate, which is correct and must not be mistaken for a tuning result.
- **`metrics.json` is not byte-comparable between runs.** `generated_at`, `wall_seconds` and the latencies differ every time, so a diff needs those fields excluded. Routing and the governance block *are* identical run to run, which is what NFR-08 actually requires.
- **Where the run's own timing sits against NFR-01.** p95 under 3 seconds is per ticket on the automated path; with the stub there is no model call, so the figure will be flattering. It has to be re-measured once drafting lands.

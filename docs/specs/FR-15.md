# FR-15 · The model provider client: timeout, retries, backoff, circuit breaker, cache

Spec written from `docs/PRD.md` FR-15 with prompt PR-06 v1.0, before any code. Modules: `src/ticketing_agent/provider.py`, with settings in `src/ticketing_agent/config.py`.

## 1 Purpose

"When the model provider times out, rate-limits or is unavailable, the system shall retry with backoff, then escalate the ticket with its context and carry on with the run."

PRD acceptance criterion: *with the provider disconnected, the run completes and every ticket is escalated and logged.* The Build Specification makes the same demand twice: A11 ("each condition is induced, including disconnecting the model provider entirely; the system degrades and continues rather than stopping") and §07 ("free tiers throttle; handling that with backoff, queuing and caching is part of the engineering, not an obstacle to it"). NFR-02 adds availability and "tickets out = tickets in"; NFR-07 adds zero spend; NFR-08 adds determinism.

This component decides nothing about a ticket. Its whole job is to make a model call boring: either a usable response, or a typed failure the pipeline can escalate on, never an exception nobody expected and never a silent empty string.

Calls go out through **LangChain**'s chat model and structured replies come back as **Pydantic** objects (D-31). The retry schedule, the backoff cap, the circuit breaker and the prompt-version-keyed cache stay in this module rather than being delegated, because A11, NFR-08 and NFR-07 are requirements no library implements for us — and because `FakeTransport` then exercises that code for real in every test instead of replacing it.

## 2 Inputs and outputs

### Settings (`config.py`, from `.env`; no other module reads `os.environ`)

| setting | default | meaning |
|---|---|---|
| `llm_api_key` | — | required for a real call; never logged, never in an exception |
| `llm_base_url` | `https://openrouter.ai/api/v1` | OpenRouter or Groq; both are OpenAI-compatible |
| `model_name` | **required** | the free-tier model id (NFR-07); no default in code |
| `judge_model_name` | from `.env` | a different free model, for PR-05 |
| `llm_timeout_seconds` | 20 | per attempt |
| `llm_max_retries` | 3 | attempts after the first |
| `llm_cache_path` | `./storage/llm_cache.sqlite` | persistent response cache |
| `breaker_failure_threshold` | 5 | consecutive failures before the circuit opens |
| `breaker_cooldown_seconds` | 60 | how long it stays open |

`model_name` has **no default in code**: a missing `MODEL_NAME` refuses to start rather than silently choosing a model, because on OpenRouter the free endpoints carry a `:free` suffix and the bare id is the paid one (NFR-07). `docs_path` and `training_tickets_path` have no defaults either — CLAUDE.md forbids a hardcoded data file name anywhere. A malformed numeric setting raises `ConfigError` instead of falling back to the placeholder, which matters most for the two thresholds the author sets from a sweep.

### Input to a call

`complete(messages, *, prompt_id, prompt_version, max_tokens=None)`. `messages` is the OpenAI-shaped list the prompt builder produced; customer text is already inside `<ticket>` tags by then (FR-12 §3.1), which this module never undoes.

### Output: `ProviderResponse`

| field | type | meaning |
|---|---|---|
| `text` | `str` | the model's reply, never empty (an empty reply is a failure, §3.5) |
| `model`, `model_version` | `str` | what answered, for the decision log's `model` block (FR-13) |
| `prompt_version` | `str` | passed through to the log |
| `cached` | `bool` | true when no call was made |
| `attempts` | `int` | how many attempts this took, 1 when cached |
| `latency_ms` | `float` | measured end to end |
| `provider_requests` | `int` | requests that actually reached the provider **on this call**; this is what FR-13 stores per row as `model_calls`. A call that succeeded on attempt 3 made three requests, and a free tier throttles on requests, not on successes |

`ProviderClient.provider_requests`, `.completions`, `.cache_hits`, `.failures`, `.cache_read_failures` and `.cache_write_failures` accumulate over a **run**, which is what NFR-07 reports. They are deliberately not the same numbers as the per-row ones: FR-13 sums its columns across rows, so writing a run total into every row would multiply it.

`complete_structured(..., schema=Model)` returns a `StructuredResponse`: the validated Pydantic object, the `ProviderResponse` that produced it, parser `notes` for the decision log, and whether a repair attempt was needed.

### Failures

| exception | when | what the pipeline does |
|---|---|---|
| `ProviderUnavailable` | timeouts, rate limits, 5xx, connection errors, unusable output, all retries spent, or the circuit is open | escalate with reason `provider_unavailable`, carry on (FR-15) |
| `ProviderError` | 400, 401, 402, 403, 404, 422 — a bad request, a bad key, an exhausted allowance or a retired model id | escalate the same way, but retrying is pointless so it fails at once |
| `MalformedModelOutput` | the reply never validated against its schema, even after one repair | escalate with the schema name and the attempt count |

All derive from `ProviderFailure`, so the pipeline catches one thing. **Nothing else leaves this module**: a non-dict `choices` element, a corrupt cache row and a hostile `Retry-After` were each found escaping untyped in review, and each would have stopped a run rather than one ticket (D-32). `ProviderUnavailable` and `MalformedModelOutput` carry `attempts`, `elapsed_ms`, `prompt_version` and `provider_requests` as attributes, so FR-13's row never has to be built by parsing a message.

### Transport

The client talks to a `Transport` protocol (`send(request) -> dict`), not to an SDK directly. `LangChainTransport` is the real one, wrapping `ChatOpenAI` with `temperature=0`, our timeout and `max_retries=0` (D-31); `FakeTransport` is scripted and is what every test uses, so the retry, backoff, breaker and cache logic is exercised for real rather than replaced. A fake that stood in for the whole client would leave exactly the code FR-15 is about untested.

## 3 Decision rules, in order

1. **Determinism first** (NFR-08). Every request carries `temperature = 0`, no `top_p`, and the configured model. The same messages and prompt version therefore ask for the same answer, and the cache makes that answer stable across runs.
2. **Cache before calling** (NFR-07, Build Spec §07 "caching is encouraged"). The key is `sha256` of the canonical JSON of `{base_url, model, prompt_id, prompt_version, messages, temperature, max_tokens}` — the base url included, because the same model id on OpenRouter and on Groq is not the same model. A hit returns immediately with `cached = True` and no call. **The prompt version is in the key**, so bumping a prompt version (prompts/README.md's rule) cannot serve an answer the old prompt produced.
3. **One attempt, then retry with backoff.** Retryable: a timeout, a connection error, 429, or any 5xx. The delay before attempt *n* is `0.5 × 2ⁿ⁻¹` seconds — 0.5, 1, 2 — deterministic, with no jitter, so a run's timing is reproducible and a test can assert it. A `Retry-After` header, when present, overrides the computed delay: a free tier that tells us when to come back is worth obeying. **Every wait is clamped to `[0, 60] s`**: a negative value would crash `time.sleep` and an hour-long one would defeat the bound the breaker exists to give (A11), so neither a bug nor a hostile header can stall or stop a run.
4. **Not everything is worth retrying.** 400, 401, 402, 403, 404 and 422 mean the request, the key, the allowance or the model id is wrong; retrying three times changes nothing and wastes the free tier. They raise `ProviderError` at once. 404 in particular is a retired or mistyped model id, the commonest free-tier mistake — retrying it would report a configuration error as an outage.
5. **Unusable output is a failure, not a response.** No choices, a missing message, or text that is empty or whitespace: retried like a timeout, and if it persists, `ProviderUnavailable`. Returning `""` would let an empty answer reach a customer through a code path nobody was watching.
6. **A circuit breaker bounds a dead provider**, as an explicit `closed / open / half_open` state machine with the failure count as evidence rather than a lever (D-32). After `breaker_failure_threshold` consecutive failures the circuit **opens** and further calls fail immediately with `ProviderUnavailable` without touching the transport, until `breaker_cooldown_seconds` have passed. It then goes **half-open**: exactly **one** trial attempt is allowed, whatever `llm_max_retries` says, because retrying a provider already known to be down is what the breaker exists to prevent. Success closes it and resets the count; any failure, retryable or not, re-opens it. This is what makes the A11 outage run finish: 120 tickets × 4 attempts × a 20-second timeout is over two hours, while a breaker that opens after five failures turns the rest of the run into instant escalations.

  **A cached reply is still served while the circuit is open**, because the cache is consulted before the breaker. An outage must not stop the part of a run that needs no provider at all.
7. **Nothing about the key or the customer's words is ever logged or raised.** Exception messages name the status, the attempt count and the elapsed time. The API key is never in a message, a `repr`, or the cache. Message content is never in an exception, because exceptions end up in logs (NFR-04).
8. **The client never decides a ticket's fate.** It raises; routing escalates. There is no fallback answer, no "best effort" text, no degraded model.

## 4 Failure behaviour

- **Missing data:** no messages, or an empty message list, is a programming error and raises `ValueError` before any call.
- **No API key:** a real `HttpTransport` refuses to start, with a message naming `.env` and `LLM_API_KEY` but never printing what was found. Tests never need a key because they use `FakeTransport`.
- **Empty retrieval:** not this component's concern.
- **Model provider error:** the whole of §3.3 to §3.6.
- **Invalid model output:** §3.5. Parsing the *content* (JSON from PR-01, PR-03) belongs to the caller; this module only guarantees the text is non-empty and says which prompt version produced it.
- **The cache cannot be opened, read or written** (locked, disk full, read-only volume, a corrupt row): the call proceeds regardless. A cache is an optimisation, and losing an entry is not a reason to fail a ticket — the opposite of the decision log, where losing a row is fatal (D-27). An unopenable cache degrades the client to no cache rather than killing the run before a single ticket is processed. Failures are counted in `cache_read_failures` and `cache_write_failures`, and `cache_available` says whether there is a cache at all, because a silently cache-less run is non-reproducible (NFR-08) and spends the free tier on every call (NFR-07). A stored reply this module cannot use is **dropped and refetched**, never served and never counted as a hit.
- **Invalid structured output:** `complete_structured` allows exactly one repair attempt, telling the model in our own words what was wrong with the shape. The repair message never quotes the reply, so customer text is not echoed back into a prompt. A reply that still does not validate is `MalformedModelOutput`.

## 5 Decision-log fields

The client writes no rows itself; it supplies what FR-13 records: `model_name`, `model_version`, `prompt_version`, `model_calls`, `cache_hits`. When it raises, the caller logs `decision = escalate`, `reason = provider_unavailable`, `requirement_ids = ["FR-15"]`, with the attempt count and elapsed time in `detail` and `explanation` saying in plain words that the provider could not be reached.

## 6 Acceptance tests

Named `test_T_FR15_n_...`. Every test uses `FakeTransport`: no network, no API key, and the real retry, backoff, breaker and cache code runs.

1. **T-FR15-1** Every request carries `temperature = 0` and the configured model; no `top_p` is sent.
2. **T-FR15-2** The same call twice makes **one** transport call; the second is `cached`, returns identical text, and `cache_hits` is 1.
3. **T-FR15-3** The cache persists across client instances: a new client on the same path replays without calling.
4. **T-FR15-4** A different `prompt_version` is a different cache key, so a bumped prompt is never answered from the old prompt's cache.
5. **T-FR15-5** A timeout is retried and then succeeds; `attempts` is 2 and the response is not cached-flagged.
6. **T-FR15-6** A 429 is retried; a `Retry-After` header overrides the computed backoff.
7. **T-FR15-7** Backoff delays are exactly 0.5, 1, 2 seconds, in order, and deterministic.
8. **T-FR15-8** All retries spent raises `ProviderUnavailable`, and the transport was called `llm_max_retries + 1` times.
9. **T-FR15-9** A 401 or 400 raises `ProviderError` immediately, with exactly one transport call.
10. **T-FR15-10** Output with no choices, or with empty text, is retried and then raises `ProviderUnavailable` — never returns `""`.
11. **T-FR15-11** The circuit opens after `breaker_failure_threshold` consecutive failures: the next call raises without touching the transport.
12. **T-FR15-12** After the cooldown the circuit is half-open: one trial call is made, and success closes it and resets the failure count.
13. **T-FR15-13** A half-open trial that fails re-opens the circuit.
14. **T-FR15-14** The A11 shape: a provider that is down for a whole run of 120 calls raises every time, the run completes, and transport calls stay bounded by the breaker rather than growing with the ticket count.
15. **T-FR15-15** A success resets the consecutive-failure count, so intermittent failures never open the circuit.
16. **T-FR15-16** Neither the API key nor any message content appears in an exception message or a `repr` of the client (NFR-04).
17. **T-FR15-17** A cache that cannot be written does not fail the call; `cache_write_failures` records it.
18. **T-FR15-18** Empty `messages` raises `ValueError` before any transport call.
19. **T-FR15-19** `ProviderUnavailable` and `ProviderError` are both `ProviderFailure`, so one `except` catches everything a caller must escalate on.
20. **T-FR15-20** The real transport without an API key refuses to construct, and the message names `.env` and `LLM_API_KEY` without printing a value. Without a `MODEL_NAME` it refuses too.

Added after the row 4 review (D-32) and for the LangChain/Pydantic layer (D-31):

21. **T-FR15-21** A malformed payload — a non-dict `choices` element, a string where an object was due, `None` — is a typed `ProviderFailure`, not an `AttributeError` that would stop the run.
22. **T-FR15-22** A corrupt cache row is a miss, is counted in `cache_read_failures`, and the call proceeds.
23. **T-FR15-23** A stored reply that cannot be used is dropped and refetched, and is not counted as a cache hit.

26. **T-FR15-26** A `ProviderError` while half-open re-opens the circuit, and the state stays honest afterwards: no primed counter, no permanently "open" report while calls are in fact going through.
27. **T-FR15-27** A cached reply is served while the circuit is open.
28. **T-FR15-28** `max_tokens`, the configured timeout and the answering model id reach the transport and the response; `model` and `model_version` are what FR-13 logs.
29. **T-FR15-29** A different model can be asked for one call (the PR-05 judge), and the default is unchanged afterwards.
30. **T-FR15-30** The cache file contains no readable customer text and no key: the key is a hash.

32. **T-FR15-32** Timeout and connection failures map to a retryable `ProviderTimeout`.
33. **T-FR15-33** An SDK exception this module has never seen is still a `ProviderFailure`, and its message is not repeated (a provider's body may echo the request).
34. **T-FR15-34** A well-formed draft becomes an `AnswerDraft`, with `text`, `cited_ids` and `uncited_sentences()` derived from it.
35. **T-FR15-35** The prompts' own rules are enforced: an unanswerable draft with no reason, an answerable one with no sentences, a supported sentence with no quote, and a handover missing either half all fail.
36. **T-FR15-36** An uncited claim is reported by `uncited_sentences()` rather than rejected: FR-11 is the guardrails' judgement, not the parser's.
37. **T-FR15-37** JSON is recovered from code fences and surrounding prose, and the recovery is noted.
38. **T-FR15-38** A brace inside a string does not confuse the object scanner.
39. **T-FR15-39** An unusable reply raises `SchemaError` whose message does **not** quote the reply (it reaches the log; NFR-04).
40. **T-FR15-40** Unexpected fields are ignored but reported as `unexpected_field:{name}`, so prompt drift is visible.
41. **T-FR15-41** A grounding check cannot return two verdicts for one sentence.
42. **T-FR15-42** The parsed models are immutable: a draft cannot be edited into compliance after the guardrails have seen it.
43. **T-FR15-43** `complete_structured` returns a validated object with the call that produced it.
44. **T-FR15-44** Exactly one repair attempt is made, and its message never echoes the bad reply.
45. **T-FR15-45** A reply that never validates raises `MalformedModelOutput` carrying the schema name; `repair=False` makes exactly one call.

## 7 Open questions

- **The cache never expires.** A cached answer from a week ago is served today, which is what makes runs reproducible but also means a documentation change does not invalidate anything (the doc text is in the prompt, so in practice it does — but only if the same chunk is retrieved). No TTL is implemented. Confirm that reproducibility beats freshness here; it is the right trade for an assessed run and the wrong one for production.
- **The breaker is per client instance, not per model.** With two models in play (the drafting model and the PR-05 judge) one dead model opens the circuit for the other, since `complete(model=...)` shares the client. Per-model breakers are a small change; not done because nothing yet calls two models in one run.
- **`0.5 × 2ⁿ` with no jitter.** Deterministic and testable, but if this ever ran as several concurrent workers they would retry in lockstep. Single-process runs make that moot today.
- **The real transport's error mapping is tested by constructing SDK-shaped exceptions** (T-FR15-31 … 33), not by calling a provider. That covers the mapping, which is the part with judgement in it, but not the SDK's actual exception types, which could change under us on a version bump. A recorded-response integration test would close the gap; the free tier makes one awkward to run in CI.
- **Free-tier rate limits are not measured.** The spec handles 429 when it arrives, but nothing tracks the remaining allowance, so a long run could exhaust it silently. Build Spec §07 says to raise cost as a design issue rather than pay; a token counter per run would make that visible. Worth adding at row 6 with the metrics report.

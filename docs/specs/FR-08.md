# FR-08 · Intent classification, and FR-05 · urgency, both with calibrated confidence

Spec written from `docs/PRD.md` FR-08 and FR-05 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/classify.py`. One component serves both requirements because they share the embedding and the calibration machinery; the queue ordering half of FR-05 is listed here and implemented with the API at row 16.

## 1 Purpose

FR-08: "The system shall classify each ticket into one of the 22 intents with a confidence between 0 and 1 and the alternatives it considered, and fall back to `unclear_request` rather than raising an error."

FR-05: "The system shall classify urgency at ingestion and order the escalation queue by urgency, then age, showing the urgency, its confidence and the reason."

PRD acceptance criteria: *every output has intent, confidence and alternatives; per-class precision and recall in the metrics report* (FR-08), and *every ticket has an urgency and confidence; the escalation queue export is sorted by urgency then received_at* (FR-05). The Build Specification's "Classify" section adds two things in plain words: the confidence must "reflect the actual probability of being correct", and the component must record "the alternatives it considered, not only the option it chose". NFR-03 puts numbers on it: intent precision ≥85% per class, and **stated confidence within 5 points of observed accuracy** — which the Evaluation Framework §3 says is demonstrated with a calibration table, and calls the thing students usually skip.

## 2 Inputs and outputs

### Input

`Ticket` (FR-07). Only `ticket.text` is read — never `raw["labels"]`, which is how a classifier could accidentally score 100%. Training reads a labelled ticket file given by path (`TRAINING_TICKETS_PATH`; nothing hardcoded), and only the development set: tuning against validation is forbidden (CLAUDE.md).

### Output: `Classification`

| field | type | meaning |
|---|---|---|
| `intent` | `str` | one of the 22, or `unclear_request` as the fallback |
| `intent_confidence` | `float` | calibrated probability in `[0, 1]` |
| `intent_alternatives` | `tuple[tuple[str, float], ...]` | the next best classes with their probabilities, highest first |
| `urgency` | `str` | `low` · `medium` · `high` |
| `urgency_confidence` | `float` | calibrated probability in `[0, 1]` |
| `urgency_reason` | `str` | **readable evidence**, see §3.4 |
| `evidence` | `tuple[tuple[str, str, float], ...]` | the nearest labelled training tickets: id, its label, similarity |
| `fallback` | `bool` | true when the model could not be used and the defaults were returned |
| `model_fingerprint` | `str` | which trained model produced this, for the decision log |

These map onto FR-13's columns directly: `prediction_value`/`prediction_confidence`, `intent`, `urgency`, `intent_alternatives`.

### Public API

- `train(tickets_path, *, embedder=None) -> TrainedClassifier` — fits, cross-validates and returns the model with its report.
- `TrainedClassifier.save(path)` / `load(path)`.
- `IntentClassifier(model).classify(ticket) -> Classification` — never raises.
- `calibration_table(probabilities, correct, bands=5) -> tuple[CalibrationBand, ...]`
- `order_escalation_queue(items) -> tuple[...]` — FR-05's ordering, used by the API at row 16.

## 3 Decision rules, in order

### 3.1 The model, and why this one

D-03 chose embeddings plus logistic regression over asking the language model. The reasons hold and are now measurable: routing must be deterministic (NFR-08) and a model's self-reported confidence is not calibrated, while a fitted classifier's can be; it is free (NFR-07); and it is fast enough that NFR-01's 3-second budget is spent on retrieval and drafting instead.

1. **Features are the embedding of `ticket.text`**, from the same all-MiniLM-L6-v2 function retrieval uses (D-02), so a ticket is embedded once per run and both components share it.
2. **`LogisticRegression` wrapped in `CalibratedClassifierCV`**, 5-fold stratified, `method="sigmoid"` for the *per-class probabilities*. Sigmoid rather than isotonic there because the classes are small: 22 intents over 500 tickets is 13 to 29 examples each, and isotonic on 13 points fits noise.

  **The confidence the system states is calibrated separately** (D-40). Per-class sigmoid calibration over 22 classes left the stated confidence about 30 points *below* observed accuracy, and NFR-03 is a claim about the number the system reports, not about the whole distribution. So a one-dimensional logistic fit maps the model's top probability onto observed correctness. Logistic and not isotonic: isotonic's flat regions emit **exactly 1.0**, which on this data meant 488 of 500 tickets stating certainty from a 94%-accurate classifier and left FR-02 with four distinct values to threshold on.

  **The estimator that is measured is the estimator that ships**, inner calibration CV included. A different inner CV shifted the top-probability distribution by 7.5 points, which would have fitted the calibrator to a distribution the shipped model does not produce.
3. **Deterministic**: `random_state` fixed, classes in sorted order, no shuffling that is not seeded. The same ticket and the same model always give the same intent, confidence and alternatives.
4. **Urgency is a second classifier over the same embeddings**, not a rule derived from intent: only 2 of the 22 intents have an urgency that is even 80% consistent, so intent does not determine urgency in this data.

### 3.2 Classifying one ticket

5. **Alternatives are the rest of the ranking**: the top classes after the chosen one, capped at three, each with the model's **raw** probability. They are a ranking, not calibrated confidences — the calibrator maps the *top* probability onto accuracy and means nothing applied to the others — and the field is documented as such so an agent reading a handover is not comparing two scales. The Build Specification asks for what was considered, not only what was chosen, and FR-01's handover carries them to the agent.
6. **Never raise.** Any failure — an unusable model, an embedder that dies, an empty text — returns `Classification(intent="unclear_request", intent_confidence=0.0, urgency="medium", fallback=True)` with the cause in `urgency_reason`. FR-08 says this in as many words, and FR-09 escalates `unclear_request` by rule, so the fallback is safe by construction rather than by luck.
7. **A missing confidence counts as low, never high** (FR-02's rule, restated here because this is where confidence is produced). The fallback's 0.0 is below any threshold the author can choose.

### 3.2b Grouped folds, because this dataset repeats itself

**This is the measurement the row turned on** (D-39). The 500 development tickets hold only **215 distinct bodies**, which collapse into about **96 clusters** once near-identical wordings are merged, and every repeated body carries the same intent. Row-wise cross-validation therefore trains and tests on the same wording, and grouping by exact body is not enough either because most bodies have a same-intent paraphrase elsewhere in the set. Folds are grouped by **wording cluster** (union-find over ≥0.85 character similarity), and the row-wise figure is reported beside it so the size of the leak stays visible. Measured with the real embedder: **88.6% cluster-grouped against 99.6% row-wise.**

The fold count is reported as the count actually used, which is usually fewer than requested: a class with four distinct wordings cannot be split five ways.

### 3.3 Calibration

8. **The calibration table is produced by cross-validation, never on the training fit**, and the table's confidences are **cross-fitted**: each half is scored by a calibrator fitted only on the other half, grouped so no wording crosses. Scoring a calibrator on its own fit reported a 0.0-point gap — the same in-sample mistake the grouped folds exist to avoid. Five equal bands over `[0, 1]`; for each, the number of predictions, the mean stated confidence, the observed accuracy, and the gap. NFR-03 is met when every populated band's gap is within 5 points, and the report states which bands are large enough to claim that of.
9. **The report says which bands are too small to judge.** With 500 tickets a high-confidence band may hold 20 predictions, and a 5-point claim over 20 predictions is noise. Bands under 25 predictions are flagged, as the fairness tables flag small segments.

### 3.4 The reason FR-05 asks for

10. **The reason is nearest-neighbour evidence, not a fabricated rationale.** A logistic regression over embeddings has no features a support manager could read, so inventing a sentence about "keywords" would be a lie. Instead the classifier returns the **nearest labelled training tickets** by cosine similarity, and the reason reads: `closest to DEV-0123 (high, 0.81), DEV-0456 (high, 0.77)`. That is true, checkable, and exactly what an agent needs to judge the call. It is also why `evidence` is a first-class field rather than a debug aid.

### 3.5 Fingerprinting and persistence

11. **A trained model carries a fingerprint** of the embedder signature (by output, per D-33), the training file's content hash, the class list and the trainer version. Loading a model whose fingerprint does not match the embedder in use is a failure, not a silent mismatch — the lesson of D-33, where a stale index would have been served.
12. **A model is an artefact, not a runtime surprise.** It is trained by `scripts/train_classifier.py` and loaded from `CLASSIFIER_PATH`. The harness never trains during a run: a gate run must not depend on fitting a model, and training during evaluation would risk touching validation data.

## 4 Failure behaviour

- **Missing data**: an empty or whitespace `ticket.text` returns the fallback (rule 6), not an exception.
- **No trained model** at `CLASSIFIER_PATH`: `IntentClassifier` construction fails loudly with a message naming the script that builds one — a run with no classifier must not quietly classify everything as `unclear_request` and look like a calibration result.
- **A fingerprint mismatch**: the same, loudly. Serving predictions from a model trained on different embeddings is worse than having none.
- **Empty retrieval / model provider error / invalid model output**: not applicable. No model provider is involved, which is why classification still works during an outage (A11) and costs nothing (NFR-07).

## 5 Decision-log fields

Classification writes a `continue` row (FR-13 §3.1) with `stage = "classification"`, `prediction_value` = the intent, `prediction_confidence` = its calibrated probability, `intent`, `urgency`, `urgency_confidence`, `intent_alternatives`, `requirement_ids = ["FR-08", "FR-05"]`, `prompt_version = null` (no model call) and the model fingerprint in `detail`. The Governance Framework's minimum record names `prediction` and `alternatives` explicitly, which is why both are columns rather than notes.

## 6 Acceptance tests

Named `test_T_FR08_n_...` and `test_T_FR05_n_...`. Offline, with an injected deterministic embedder: the behaviour is what these test. **Real accuracy and calibration are measured by `scripts/train_classifier.py`** into `evaluation/reports/classifier_calibration.md`, because a hashing embedder can say nothing about whether the classifier is any good — the same division as FR-10.

1. **T-FR08-1** Every classification has an intent from the 22, a confidence in `[0, 1]`, and alternatives — for every ticket in the development set, with no exception raised.
2. **T-FR08-2** Alternatives exclude the chosen intent, are ordered by descending probability, are capped at three, and every probability is in `[0, 1]`.
3. **T-FR08-3** An empty, whitespace-only or malformed ticket returns the `unclear_request` fallback with confidence 0.0 and `fallback = True`, never an exception.
4. **T-FR08-4** A broken embedder and a broken model each produce the fallback, not an exception (FR-08's "rather than raising an error").
5. **T-FR08-5** Determinism: the same ticket classified twice gives identical intent, confidence, alternatives and evidence (NFR-08).
6. **T-FR08-6** The classifier never reads ground truth: with `labels` present it behaves identically to the same ticket with `labels` stripped.
7. **T-FR08-7** Training and classification use the path given, and the training file is the development set only; pointing at another file trains a different model.
8. **T-FR08-8** A model saved and reloaded classifies identically, and its fingerprint survives the round trip.
9. **T-FR08-9** A model loaded with a different embedder than it was trained with is rejected loudly, not served.
10. **T-FR08-10** `calibration_table` is arithmetically right on known inputs: band membership, counts, mean stated confidence, observed accuracy and the gap, including an empty band and a single-item band.
11. **T-FR08-11** The calibration table comes from cross-validated predictions, not from the training fit: a model asked to report its own training accuracy would be near-perfect and the test pins that the reported figures are out-of-fold.
12. **T-FR08-12** Per-class precision and recall are produced for every class present in the training data, with support counts (the metrics report's technical block consumes these).
13. **T-FR05-1** Every ticket gets an urgency from `low`/`medium`/`high` and a confidence in `[0, 1]`.
14. **T-FR05-2** The urgency reason is readable evidence naming real training ticket ids with their labels and similarities, and those ids exist in the training file.
15. **T-FR05-3** `order_escalation_queue` sorts by urgency (high, medium, low) then by `received_at` oldest first, and a ticket with no timestamp sorts last rather than crashing.
16. **T-FR05-4** The queue ordering is stable for equal keys and deterministic across calls.
17. **T-R2-2** (review row R2) Two escalated tickets of different urgency, **submitted through the API** rather than written into the log by hand, come back from `/queue` urgency-first. T-FR05-3 inserts its own rows, so it passed throughout the period in which the pipeline never filled the `urgency` column and the queue was in fact oldest-first.
18. **T-R2-5** (review row R2) The `urgency_reason` the classifier produced reaches the decision-log row and is what `/queue` serves under that name. The escalation detail — a different question — is served under `detail`.
Added after the row 8 review:

18. **T-FR08-15** The estimator that is measured is the estimator that ships: class weighting **and** inner calibration CV.
19. **T-FR08-16** The stated confidence is calibrated, not the raw probability, and the reported table is cross-fitted.
20. **T-FR08-17** The stated confidence is not degenerate: at least 20 distinct values across the development set, fewer than a quarter at near-certainty, and a usable range. A confidence that cannot vary is not a confidence.
21. **T-FR08-18** The calibration verdict is measured and reported, with bands too small to judge flagged — the test asserts the measurement is honest, **not** that the target is met, because on this data it is not in every band.
22. **T-FR08-19, T-FR08-20** A missing, corrupt, wrong-typed or stale model fails loudly rather than becoming a silent run of `unclear_request`.
23. **T-FR08-4b** There is no flag that disables the embedder check.
24. **T-FR05-5** An unrecognised urgency is treated as `medium`, never sorted below `low` — an escalation queue must not guess downwards.
25. **T-FR05-6** Ages compare as times, not as strings: an offset timestamp, a `Z` timestamp and an epoch integer order correctly, and an unparseable one sorts last.
26. **T-FR05-7** The reason never cites the ticket itself, which would be circular and would put another ticket's ground-truth urgency into the log.

17. **T-FR08-13** A `Classification` maps onto FR-13's columns without translation: the fields a `DecisionEntry` needs are present and of the right types.

## 7 Open questions

- **Resolved (D-40): sigmoid for the per-class probabilities, logistic for the stated confidence.** Isotonic was tried for the confidence and saturated. With more data, isotonic for the confidence would likely be better than logistic; revisit then.
- **NFR-03 is met where it matters and fails in one thin band.** The band holding 475 of 500 predictions is within 2.3 points; one band of exactly 25 predictions is 42.6 points out. The report states both rather than quoting the worst number alone, and whether that is acceptable is the author's call at row 10.
- **Three of the 22 intents are below 85% precision**, so on NFR-03's strict per-class reading the target is not met. The report names them. Merging rare classes, adding rules for them, or accepting the miss is a decision for the author, not this row.
- **22 classes over 500 tickets is 23 examples each.** NFR-03's ≥85% precision *per class* is demanding at that support, and the rarest classes are where it will fail first. The report gives per-class figures precisely so the failure is visible rather than hidden in an average, and the author decides whether to accept it, merge classes, or add rules for the rare ones.
- **Urgency has a ceiling of 73.0% and reaches 48.4%** (D-41). 67 ticket bodies carry more than one urgency label, so no model that sees only the text can beat that ceiling — it is a limit of the labelling, not of the model. `low` is effectively unreachable (0.8% recall of 128) because its embedding centroid sits 0.96 cosine from `medium`, so **FR-05's three levels are in practice two**. The queue still orders correctly; it just cannot often distinguish low from medium. Whether that is acceptable, or whether urgency needs rules rather than a classifier, is the author's call.
- **The confidence threshold that consumes this is row 9/10's decision**, not this row's. Nothing here picks a threshold.
- **Nearest-neighbour evidence exposes training tickets to agents.** The ids are CloudServe's own historic tickets, which is fine internally, but the ids must never reach a customer-facing reply. FR-12's private-data check covers the reply; this is a note for row 11 not to put evidence in the draft.

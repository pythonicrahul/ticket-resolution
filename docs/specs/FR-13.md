# FR-13 · The decision log

Spec written from `docs/PRD.md` FR-13 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/logging_store.py`.

## 1 Purpose

"The system shall write every automated decision to a persistent log with the Governance Framework fields, including prompt version and requirement IDs."

PRD acceptance criterion: *logged decisions reconcile exactly with tickets processed.* NFR-05 adds: *100% of decisions logged, with prompt version and requirement IDs*, verified by the metrics report reconciling decisions against tickets. Marcus's line in the discovery is the point of the whole thing: a decision log that answers "why did it do that?".

CLAUDE.md makes two demands this spec has to satisfy structurally rather than by convention: the row is written **before** the action is taken, and no flag, environment variable or `except` clause may skip logging.

**The field list is the Governance Framework's**, not an invention: `Capstone_Pack/03_Reference/Governance_Framework.docx` §1 specifies a "minimum record", and `governance_record()` emits a stored row in exactly that shape, with the framework's own field names and nesting. The stage and `action_taken` vocabularies are the framework's too. Build Specification A8 is the criterion this serves: "the log is opened, decisions are counted against tickets processed and must reconcile".

## 2 Inputs and outputs

### Input: `DecisionEntry`

One per decision. Built by the component that decides, from `Ticket.log_fields()` (FR-07) plus its own findings.

| field | type | source | notes |
|---|---|---|---|
| `ticket_id` | `str` | FR-07 | as supplied, duplicates and all (D-12) |
| `source_index` | `int \| None` | FR-07 | position in the input file; the reconciliation key |
| `stage` | `str` | caller | the framework's four — `classification` · `routing` · `generation` · `validation` — plus `ingest` · `retrieval` · `handover` · `pipeline`, which it does not name |
| `decision` | `str` | caller | the framework's `action_taken`: `auto_respond` · `escalate` · `block`, plus `continue` for intermediate rows (see §3.1) |
| `reason` | `str \| None` | caller | the machine code, the primary reason under FR-12 §3.4 precedence; required for `escalate` |
| `explanation` | `str \| None` | caller | **the human-readable reason**, required on every terminal row. The framework asks for "a human readable explanation of why this action followed"; the Build Specification's Route section wants it "in language a support manager could read" |
| `prediction_value`, `prediction_confidence` | `str \| None`, `float \| None` | caller | the framework's `prediction` block: what this stage decided and how sure it was |
| `threshold_applied` | `float \| None` | FR-02 | the threshold this decision was taken against. Required for `auto_respond`: the framework's confidence-floor guardrail is only demonstrable if the threshold that was applied is recorded |
| `sources_used` | `tuple[tuple[str, float], ...]` | FR-10 | doc id **with its score**, as the framework requires and as Build Specification "Retrieve" requires |
| `all_reasons` | `tuple[str, ...]` | caller | every rule that matched, in precedence order (D-16) |
| `detail` | `str \| None` | caller | pattern names, unsupported sentences, matched triggers — **never a matched private value** |
| `summary`, `uncertainty` | `str \| None` | FR-01 | the handover summary and what the system was unsure about; FR-01's criterion puts them in this log |
| `intent`, `urgency` | `str \| None` | FR-08, FR-05 | |
| `intent_confidence`, `urgency_confidence` | `float \| None` | FR-08, FR-05 | |
| `intent_alternatives` | `tuple[tuple[str, float], ...]` | FR-08 | the alternatives considered |
| `retrieved_doc_ids`, `citations` | `tuple[str, ...]` | FR-10, FR-11 | |
| `guardrail_results` | `tuple[tuple[str, bool], ...]` | FR-12 | all four checks, passes included |
| `prompt_version` | `str \| None` | caller | e.g. `PR-01 v1.0`; `null` only when no model call was made |
| `model_name`, `model_version` | `str \| None` | config | the framework's `model` block |
| `model_calls`, `cache_hits` | `int` | FR-15 | NFR-07 counts these per run |
| `latency_ms` | `float \| None` | caller | NFR-01 reports median and p95 |
| `kill_switch` | `bool` | FR-16 | true when the switch forced this decision |
| `ingest_defects` | `tuple[str, ...]` | FR-07 | |
| `channel`, `tier`, `region`, `fluency` | `str \| None` | FR-07 `segments()` | the NFR-06 segment keys |
| `requirement_ids` | `tuple[str, ...]` | caller | **never empty** |

The store adds `decision_id` (the framework's own identifier, `{run_id}:{random}`), `run_id`, `logged_at` (the framework's `timestamp`), `schema_version` and `redactions` (which fields were scrubbed or truncated, by pattern name). `retrieved_doc_ids` is derived from `sources_used` when the caller gives only the latter, so the flat list is a query convenience rather than something to keep in step by hand.

### Output: the SQLite database

Table `decisions`, one row per decision, with a surrogate `row_id INTEGER PRIMARY KEY AUTOINCREMENT` (D-12) and every field above as a column. Sequence values are JSON arrays; `logged_at` is ISO-8601 UTC written at insert time; `run_id` and `schema_version` are added by the store. Indexes on `ticket_id`, `run_id` and `(run_id, source_index)`.

Table `runs`: `run_id`, `started_at`, `input_path`, `tickets_in`, `finished_at`, `tickets_out`, so a reconciliation can be done later from the database alone.

The database lives wherever the caller says (`storage/decisions.db` by default, git-ignored). Nothing about the path is hardcoded outside the default.

### Public API

- `DecisionLog(path, run_id=None)` — creates the parent directory and schema if absent; a context manager.
- `record(entry) -> int` — validate, insert, commit, return `row_id`.
- `perform(entry, action)` — record the decision, commit it, **then** call `action()` and return its result. This is the supported way to act on a decision: the call has already written the row before the action runs. `record` stays public for the intermediate rows, so this is enforced by review and by row 14's wiring, not by the type system (§7).
- `rows(...)`, `terminal_rows(...)` — read back, JSON decoded.
- `start_run(input_path, tickets_in)` / `finish_run(tickets_out)`.
- `reconcile(tickets) -> Reconciliation`.
- `governance_record(row) -> dict` — one stored row projected into the Governance Framework's minimum-record shape, which is what an assessor opens.

## 3 Decision rules, in order

### 3.1 What counts as a decision, and what "terminal" means

`auto_respond` and `escalate` are **terminal**: they end the ticket. `block` is the framework's third action and is **not** terminal: a blocked reply is recorded as a block and the ticket then ends with an `escalate` row, so "exactly one terminal row" still holds while the block stays visible for the metrics report's "blocked by guardrails" count. Every ticket must have **exactly one** terminal row — that is what "logged decisions reconcile exactly with tickets processed" means, and it is what `reconcile` checks. `continue` rows are intermediate audit records (a classification made, a retrieval performed) that explain how the terminal decision was reached; they are not counted in reconciliation and never substitute for a terminal row.

### 3.2 Validation: a row that cannot be audited is not written

**A call that is wrong raises.** `record` raises `InvalidDecision` and writes nothing when:

1. `requirement_ids` is empty — an unattributed decision is unauditable (NFR-05).
2. `decision` is outside the vocabulary of §3.1.
3. `stage` is outside the vocabulary of §2.
4. `decision == "escalate"` and `reason` is absent — Marcus's question is "why did it do that?".
5. `model_calls > 0` and `prompt_version` is absent — if a model was called, the log must say which prompt version produced the output (FR-13's own wording, NFR-05, NFR-08).
6. `ticket_id` is blank.
7. The decision is terminal and `explanation` is missing — the framework and the Build Specification both require a human-readable reason.
8. `decision == "auto_respond"` and `threshold_applied` is absent — an automatic answer that cannot show which threshold it cleared cannot demonstrate the confidence floor (FR-02).

Every one of these is a mistake at the call site, which the tests cover, so raising is right: the alternative is a run that looks logged and is not. **None of them is reachable from ticket data** — that distinction is what the next rule protects.

**Content that is wrong is redacted, and the row is still written.** `reason`, `detail` and each of `all_reasons` are scrubbed for anything shaped like private data — an email address, a Luhn-valid card number, a national-id-shaped number, a credential assignment, a private-key marker. The value is replaced by `[redacted:{pattern}]` and the pattern name is recorded in the row's `redactions` column.

This is deliberately **not** a rejection. FR-12's own acceptance criterion is that a guardrail block *is recorded*, and FR-12 §3.2.2 defines `detail` as including "the unsupported sentence" — a sentence that may itself contain an email address. Rejecting the row would mean a decision was taken with no log row at all, breaking NFR-05's "100%" for exactly the tickets NFR-04 cares most about. Redacting keeps both: the block is recorded and the value never reaches the log. Redaction here concerns the *log*; the reply itself is still blocked, never redacted.

The patterns are linear (no backtracking) and the scrub is bounded by `MAX_TEXT_FIELD` (4000 characters), because `detail` can carry attacker-influenced text. `reason`, `detail`, `summary` and `uncertainty` are truncated at that bound with `truncated:{field}` recorded, so an over-long value is trimmed rather than rejected. Row 12 owns the canonical pattern tables; the copy here is a last-ditch scrub.

### 3.3 Writing

Every write is a single `INSERT` on a connection opened with `isolation_level=None`, so it commits as it runs and the row is durable before `perform` calls the action — a crash between the two leaves the decision on disk. SQLite runs in WAL mode with `synchronous=FULL`, so a second process (the API alongside a harness run) can read and write the same log without losing rows. T-FR13-26 pins all three settings, because changing any of them would break the guarantee while leaving every other test green.

### 3.4 Reconciliation

`reconcile(tickets)` compares the terminal rows of this run against the tickets that went in:

- **`source_index` coverage is authoritative** (D-12). Every index the tickets carry must have exactly one terminal row. This is what makes a file with duplicate `ticket_id`s reconcile honestly. A ticket with **no** `source_index` cannot be reconciled that way, so it is reported in `tickets_without_index` and makes `ok` false — silently skipping it would turn D-12's key off whenever a caller forgot `index=`.
- Ticket-id checks are reported alongside: `missing` (a ticket with no terminal row), `extra` (a terminal row for a ticket that was not in the input), `duplicated` (more than one terminal row for one ticket).
- `duplicate_input_ids` is **informational**, not a failure: the input file may legitimately repeat an id (FR-07 flags it, D-12 keeps it).
- `ok` is true only when the counts match and `missing`, `extra`, `duplicated` and `index_gaps` are all empty.

`Reconciliation` also carries `counts_by_decision`, `counts_by_reason`, `redactions`, `model_calls`, `cache_hits` and `latencies_ms` — the figures the metrics report needs. `model_calls` and `cache_hits` sum over every row of the run (NFR-07 counts calls, wherever they happened); `latencies_ms` comes from terminal rows only, because NFR-01 measures a ticket end to end, not a stage.

## 4 Failure behaviour

- **Missing data:** absent optional fields are stored as SQL `NULL`. The five required fields are checked in §3.2.
- **The database cannot be written** (locked, permission denied, disk full): retry once, then append the row as one JSON line to `<db>.fallback.jsonl` and raise `DecisionLogUnavailable`. **If the fallback cannot be written either** — the usual cause is the same permission problem — the exception says so and still carries the failure; it is always a `DecisionLogError`, never a bare `sqlite3.Error` or `OSError`, so a caller has one thing to catch and a per-ticket `except` cannot mistake it for an ordinary ticket failure. Opening the log and the `runs` writes behave the same way. The decision is preserved for the audit either way, and the run stops rather than continuing unlogged — the one case where stopping beats carrying on, because an unauditable run fails FR-13 and NFR-05 for *every* ticket, not one. The harness reports it as a run-level failure (FR-14).
- **Model provider error:** not reachable; the store makes no model calls.
- **Invalid model output:** not applicable. The caller records what it saw, with `prompt_version` set.
- **A ticket failing mid-pipeline:** its terminal row is still required. `perform` writes the row first, so a raising action leaves the decision logged, which is the correct record: the decision *was* taken.

## 5 Decision-log fields

This component *is* the log. Its own rows carry `stage = "pipeline"` and `requirement_ids = ["FR-13"]` for the two run-level records (`start_run`, `finish_run`), which are written to the `runs` table rather than `decisions`.

## 6 Acceptance tests

Named `test_T_FR13_n_...`, offline, on a temporary path. No network, no API key. T-FR13-16 also parses the module and asserts that **every** `except` ends in a `raise` (or reports failure), which a list of suspicious names cannot do.

1. **T-FR13-1** The schema is created at any given path, including a directory that does not exist yet; `decisions`, `runs`, the indexes and `schema_version` are all present.
2. **T-FR13-2** A row carrying every field round-trips: JSON sequence fields come back as lists, `None` stays `None`, floats keep their value.
3. **T-FR13-3** Empty `requirement_ids` raises `InvalidDecision` and writes nothing.
4. **T-FR13-4** `escalate` with no `reason` raises `InvalidDecision`.
5. **T-FR13-5** `model_calls > 0` with no `prompt_version` raises `InvalidDecision`; with `prompt_version` it is accepted.
6. **T-FR13-6** A `detail`, `reason` or `all_reasons` entry containing an email address, a Luhn-valid card number, a national-id-shaped number or a credential is redacted to `[redacted:{pattern}]`, the pattern is recorded in `redactions`, **and the row is still written** — the log cannot become the leak, and a decision is never dropped for what it contains.
7. **T-FR13-7** An unknown `decision`, an unknown `stage` and a blank `ticket_id` each raise `InvalidDecision`.
8. **T-FR13-8** `perform` writes and commits the row **before** the action runs: an action that reads the log from a separate connection sees its own row already there.
9. **T-FR13-9** An action that raises leaves the decision row in place and propagates the exception.
10. **T-FR13-10** A clean run of the engineered corpus reconciles: `ok` is true, one terminal row per ticket, `counts_by_decision` matching.
11. **T-FR13-11** `reconcile` detects each discrepancy: a missing terminal row, an extra one, a duplicated one, and an `index_gap`.
12. **T-FR13-12** A file with duplicate `ticket_id`s reconciles on `source_index` coverage, and `duplicate_input_ids` is reported without making `ok` false (D-12).
13. **T-FR13-13** `continue` rows do not count as terminal and do not break reconciliation.
14. **T-FR13-14** Rows persist across close and reopen: a second `DecisionLog` on the same path reads what the first wrote.
15. **T-FR13-15** When the write fails, the row is appended to `<db>.fallback.jsonl` and `DecisionLogUnavailable` is raised — nothing is silently dropped.
16. **T-FR13-16** No bypass: no public function takes a parameter that disables or defers writing, and a search of the source finds no flag, env var or `except` that skips a write (CLAUDE.md).
17. **T-FR13-17** Two `DecisionLog` instances on the same path both write and both sets of rows are readable (WAL).
18. **T-FR13-18** The same decision logged twice produces two rows with identical governance fields, differing only in `row_id`, `logged_at` and `run_id` — the store adds nothing that would make a rerun's decisions look different (NFR-08).
19. **T-FR13-19** `Ticket.log_fields()` from FR-07 feeds `DecisionEntry` without translation: the segment keys, `ingest_defects` and `received_at` arrive in the row unchanged.

29. **T-FR13-29** A blocked reply is recorded with `action_taken = block`, is not counted as terminal, and the ticket still reconciles through its `escalate` row.

## 7 Open questions

- **Resolved: the framework was read and the schema now matches it.** `Capstone_Pack/03_Reference/Governance_Framework.docx` §1 was checked against the reconstruction. Seven things were missing and are now implemented: `decision_id`, `model.version`, the generic `prediction` block, `threshold_applied`, `sources_used` **with scores**, the `block` action, and a human-readable `explanation` distinct from the machine `reason`. The stage vocabulary was renamed to the framework's (`classification`, `routing`, `generation`, `validation`). Nothing in the framework's minimum record is absent now, and `governance_record()` plus T-FR13-28 keep it that way. The framework asks for nothing this schema omits — no data-subject reference, no retention marker, no reviewer sign-off — so the remaining gap is retention policy, below.
- **Should the FR-01 handover `summary` be scrubbed for private data too?** It is derived from customer text, so it can carry PII, but it is also the field that makes an escalation useful to Daniel. Left unscrubbed and stored, with the strict check applied only to `reason` and `detail`, which should never contain customer text. Confirm: is the decision log an internal artefact where a summary is acceptable, or does NFR-04's "zero private data" reach it?
- **Retention.** Nothing says how long the log is kept, and a compliance reviewer will ask. No deletion path is implemented; `storage/` is git-ignored and local.
- **`continue` rows could grow large.** One row per stage per ticket is roughly 5–8 rows per ticket, so a 500-ticket run writes a few thousand. Fine locally; worth a note if this ever ran at CloudServe's 500+/week with history.
- **Whether a run-level failure should really stop the run** (§4). The alternative — carry on unlogged — breaks FR-13 for every ticket, so stopping is specified. Confirm that is the trade the author wants.
- **`perform` is the supported path, not the only possible one.** `record` is public, so a determined caller could log and act separately, or act without logging. Making `record` private would stop that but also stop the harness writing intermediate rows. Row 14 must assert that the pipeline routes every action through `perform`; until then this is a convention backed by review, not by the type system.

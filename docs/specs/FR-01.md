# FR-01 · A handover package on every escalated ticket

Spec written from `docs/PRD.md` FR-01 with prompt PR-06 v1.0, before any code. Module: `src/ticketing_agent/handover.py`, using `prompts/build/PR-02_escalation_handover_v1.0.md` and `ProviderClient.complete_structured` into `schemas.HandoverNote` (D-31).

## 1 Purpose

"The system shall attach a handover package to every escalated ticket: a short summary of the issue, the predicted intent and urgency with confidence, the retrieved articles, any draft answer, and a plain statement of what the system was unsure about."

PRD acceptance criterion: *100% of escalated tickets in a harness run carry a non-empty summary and uncertainty reason in the decision log.* The evidence is Daniel's interview and the line from Stage 1 §1 that nobody said out loud: **all 108 repeat contacts in the supplied data are on escalated tickets.** An escalation that arrives without context is how a ticket gets asked about twice.

The requirement is about coverage before quality. A note that is merely adequate on every escalation is worth more than an excellent note on most of them, because the failure mode being designed out is the empty handover.

## 2 Inputs and outputs

### Input

| name | from | used for |
|---|---|---|
| `ticket` | FR-07 | channel, subject, body — as data, inside `<ticket>` tags |
| `classification` | FR-08 | intent, confidence, alternatives, urgency — the system record |
| `decision` | FR-02 | the escalation reason, which is what the note must explain |
| `passages` | FR-10 | the retrieved articles, whether or not anything was drafted |
| `draft` | FR-11 | the draft answer, if one was written before a guardrail blocked it |

### Output: `Handover`

| field | type | meaning |
|---|---|---|
| `summary` | `str` | never empty — the PRD's criterion is about this field |
| `customer_goal` | `str` | what the customer is trying to achieve |
| `already_tried` | `tuple[str, ...]` | steps the customer says they tried; `("none stated",)` when they said none |
| `system_uncertainty` | `str` | never empty — a plain statement of what the system was unsure about |
| `relevant_passages` | `tuple[str, ...]` | chunk ids, all of which were retrieved for this ticket |
| `suggested_first_check` | `str \| None` | where a tier-two engineer might start |
| `draft_answer` | `str \| None` | the blocked or unsent draft, so the agent can reuse or reject it |
| `intent` / `intent_confidence` / `urgency` | `str` / `float` / `str` | the system record, carried verbatim from FR-08 |
| `source` | `str` | `model` or `template` — how this note was produced |
| `prompt_version` | `str \| None` | `PR-02 v1.0`, or `None` for a template note |
| `model_calls` / `cache_hits` | `int` | FR-13's per-row provider counters |

## 3 Decision rules, in order

1. **Every escalation gets a note, and nothing here raises.** The criterion is 100%, so every failure path ends in a note rather than an exception: a provider outage, a malformed reply, a missing classification and an empty retrieval all still produce `summary` and `system_uncertainty`.
2. **A ticket carrying a secret never reaches the model.** If FR-12's `secrets_in` finds a card number, a national-id-shaped number or a credential in the ticket, the note is built from the template with **no provider call at all**. FR-12 §3.1.2's rationale is that a secret "must never be embedded, cached or sent to a provider", and a handover is not an exception to it. PR-02's own masking rule stays as a second line for anything the detector misses.
3. **An injection attempt never reaches the model either.** The same argument as rule 2 in a different direction: text written to manipulate a model is not text to hand to a model. `instruction_injection_detected` takes the template.
4. **The uncertainty is written from the escalation reason, and the model's version is discarded.** Each reason has a sentence that says what the system could not settle, in the plain language FR-02 §3.8 requires. The model's `system_uncertainty` is **not** used even when it is non-empty: the system knows exactly why it escalated and the model can only guess, and on the first real run it guessed by echoing the reason code back — *"the system flagged the intent as a security incident but required escalation (must_escalate_intent)"*, which is the jargon the PRD's "plain statement" rules out (D-52). PR-02 still asks for the field, because writing it keeps the model's attention on the escalation reason while it writes the summary.
5. **`relevant_passages` is filtered to what was retrieved.** A chunk id that was not retrieved is dropped, and the note is still produced. This is deliberately the opposite of FR-11's rule: there, an unresolvable citation makes the whole reply unusable, because a customer would be misled; here the reader is a tier-two engineer who needs the note to exist, and a dropped id costs them nothing.
6. **The draft is attached when there is one.** A reply blocked by a guardrail is still evidence: the agent can see what the system was about to say and why it was stopped.
7. **Deterministic** (NFR-08): temperature 0 and the cache, so the same escalation produces the same note. The template is pure string work over the system record.
8. **The template is not a degraded mode to be avoided.** It is the guaranteed path, and the measured one: the harness reports what share of notes came from each source, so a run where the provider was down reads as such instead of looking like a quality collapse.

## 4 Failure behaviour

- **Missing data:** no classification → the note says the intent could not be determined, and `intent_confidence` is 0.0 (FR-02's rule, and FR-08's). No draft → `draft_answer` is `None`. No passages → `relevant_passages` is empty and the summary says the documentation had nothing.
- **Empty retrieval:** the note is produced. This is the common case for the 29% of tickets the documentation cannot answer, and it is exactly when a person most needs the context.
- **Model provider error:** the template note, reason recorded, run continues (A11, FR-15). No escalation is ever lost to an outage.
- **Invalid model output:** the template note. A half-parsed note is not passed to an engineer as though it were written.

## 5 Decision-log fields

`summary` and `uncertainty` are written onto the ticket's **terminal escalation row** (FR-13), which is what the PRD's criterion is measured against. Also `prompt_version` (`PR-02 v1.0` or `null`), `model_calls`, `cache_hits`, `retrieved_doc_ids`, and `requirement_ids = ["FR-01"]` plus `["FR-05"]` for the urgency it carries. FR-13 **truncates** both fields and deliberately does not scrub them (FR-13 §7 leaves that to the author), so the summary is the one place customer text reaches the log intact. The template therefore applies PR-02's rule 5 itself: a ticket whose subject or opening line carries a secret is summarised as `[secret present in ticket]` rather than quoted (D-52). A name or an ordinary address in a summary is still stored, which is the author's open question, not a defect.

## 6 Acceptance tests

Named `test_T_FR01_n_...`. All offline, through `FakeTransport`.

1. **T-FR01-1** A model note carries every field: a non-empty summary, a non-empty uncertainty, the intent and urgency with confidence, the retrieved articles, and the draft when there is one.
2. **T-FR01-2** A provider failure produces a template note with a non-empty summary and uncertainty, `source = "template"`, and no exception.
3. **T-FR01-3** A reply that cannot be parsed after the repair attempt produces a template note, not a half-filled one.
4. **T-FR01-4** A ticket containing a credential or a card number produces a template note and **zero provider requests**: the secret is never sent.
5. **T-FR01-5** An injection attempt produces a template note and zero provider requests.
6. **T-FR01-6** `relevant_passages` contains only chunk ids that were retrieved; an id the model invented is dropped and the note survives.
7. **T-FR01-7** Every escalation reason in FR-02's precedence table yields a distinct, non-empty uncertainty sentence a support manager could read, and no reason code appears in any of them. **T-FR01-7b** a model note's own `system_uncertainty` never reaches the handover, however confident it sounds.
8. **T-FR01-8** The customer's name never reaches the prompt, and the ticket text appears exactly once, inside `<ticket>` tags.
9. **T-FR01-9** The same escalation produces the same note twice, with one provider call (NFR-08, NFR-07).
10. **T-FR01-10** The note maps onto FR-13's columns, and a `DecisionEntry` built from it records with `summary` and `uncertainty` populated.
11. **T-FR01-11** Over every engineered ticket in `tests/fixtures/`, a note is produced with a non-empty summary and uncertainty — the PRD's 100% criterion, measured on the corpus designed to break things.
12. **T-FR01-12** `already_tried` is `("none stated",)` rather than empty when the customer described no steps, so an agent can tell "nothing tried" from "not extracted".

## 7 Open questions

- **Does the summary belong in the decision log at all?** It is derived from customer text, so it can carry private data, and FR-13 §7 already raises this. The PRD's criterion puts it there, so it is there; whether NFR-04's "zero private data" reaches an internal log is the author's call.
- **`already_tried` is the field PR-02 is most likely to invent.** The prompt's rule 3 says "none stated", and T-FR01-12 checks the empty case, but nothing detects a fabricated step. The 20-ticket review PR-02 describes is the only honest check, and it is the author's to run.
- **No urgency override.** The note carries FR-05's urgency as classified. Whether an enterprise ticket should be raised in the queue is a business decision the PRD leaves to Marcus (D-41).
- **The template note is terse by design.** It records what the system knew rather than reading well. If the author wants it to read like prose, that is a second prompt rather than a longer template, because the template's value is that it works when no model does.
